# 5.4 拒单实现讲解

## 1. 先确认文档允许的状态流转

5.4 用于商家拒单。允许从哪个状态拒单，需要一起看接口文档 0.4 的通用状态表：

| 当前状态 | 本接口处理 |
| --- | --- |
| 1 待接单 | 允许拒单，变为 4 已取消 |
| 2 已接单 | 拒绝，文档只允许从 2 变为 3 已完成 |
| 3 已完成 | 拒绝，终态不可再变更 |
| 4 已取消 | 拒绝重复拒单，保留原原因和更新时间 |

所以 Java 和 SQL 都检查原状态为 1。本接口不能将已接单订单直接取消。

## 2. 请求示例：路径和请求体各提供一部分参数

```http
PUT /admin/order/cancel/101
Authorization: 登录获得的原始token
Content-Type: application/json

{"cancelReason":"备料已售完，抱歉"}
```

将 101 换成本店真实的待接单订单 ID。成功返回：

```json
{"code":0,"message":"操作成功","data":null}
```

状态不允许时返回：

```json
{"code":1,"message":"当前订单状态不允许拒单","data":null}
```

## 3. Controller：接收数据并交给 Service

```java
@PutMapping("/cancel/{id}")
public Result cancel(@PathVariable("id") Long id, @RequestBody Order order) {
    orderService.cancel(id, order.getCancelReason());
    return Result.success();
}
```

- `@PathVariable("id")` 从 `/cancel/101` 得到订单 ID。
- `@RequestBody` 把 JSON 转成 Order，这里只读取 cancelReason。
- `orderService.cancel(...)` 执行成功后，Controller 才会返回成功；抛出异常则由全局异常处理器返回错误。

沿用项目已有的实体接收方式，没有将整个 Order 传给 Mapper 做全字段更新。即使请求体额外传入 id、storeId、status、amount、finishTime，真正调用更新方法时使用的仍是路径 ID、登录门店、服务端固定状态和时间。

这里没有使用 `@Validated(Order.Add.class)` 或 Update 分组，因为它们对应新增、修改订单的约束，会涉及本接口不要求的金额、请求体 ID 等字段。拒单需要的参数由 Service 单独校验，直接调用 Service 时同样有效。

## 4. Service：先检查，再写入

`OrderService.cancel(Long id, String cancelReason)` 在实现方法上添加了 `@Transactional`，依次执行：

1. 调用 `AdminContextUtil.getCurrentAdminStoreId()`，验证登录、管理员角色和门店绑定，获取可信门店 ID。
2. 要求订单 ID 非 null 且大于 0。
3. 使用 `StringUtils.hasText(cancelReason)` 拒绝 null、空串和纯空白原因。
4. 使用 `strip()` 去掉原因首尾空白；按 `ordering-ddl.sql` 中 cancel_reason 的 VARCHAR(255) 检查长度，不默默截断内容。
5. 先锁当前门店，再按订单 ID 和门店 ID 查询并锁定订单，顺序与 5.2、5.3、整店删除一致。
6. 订单不存在或不属于本店则拒绝；状态不是 1 也拒绝。
7. 获取一次服务端时间，调用 Mapper，检查影响行数必须为 1。

关键代码：

```java
if (!Integer.valueOf(1).equals(order.getStatus())) {
    throw new BizException("当前订单状态不允许拒单");
}
LocalDateTime updateTime = LocalDateTime.now();
int rows = orderMapper.cancel(id, storeId, reason, updateTime);
if (rows != 1) {
    throw new BizException("当前订单状态不允许拒单");
}
```

先调用 Mapper，再检查返回行数，沿用前面容易阅读的展开写法。更新没有生效时抛出业务异常，不会正常返回成功。BizException 是运行时异常，默认事务规则能够回滚。

## 5. Mapper：用一条有范围限制的 SQL 写入

```java
@Update("update t_orders set status = 4, cancel_reason = #{cancelReason}, update_time = #{updateTime} " +
        "where id = #{id} and store_id = #{storeId} and status = 1")
int cancel(@Param("id") Long id,
           @Param("storeId") Long storeId,
           @Param("cancelReason") String cancelReason,
           @Param("updateTime") LocalDateTime updateTime);
```

保持 EmployeeMapper 一样的注解和字符串拼接风格。`#{...}` 使用参数绑定，拒单原因作为参数交给数据库。

| SQL 部分 | 作用 |
| --- | --- |
| SET status = 4 | 目标状态由服务端固定，前端不能指定 |
| SET cancel_reason | 保存清理过首尾空白的拒单原因 |
| SET update_time | 记录本次操作时间 |
| WHERE id | 仅操作路径指定的订单 |
| AND store_id | 强制限定登录门店 |
| AND status = 1 | 真正更新时再次检查原状态 |

三个字段一次更新，避免状态改了但原因没写入。没有额外的无 WHERE 更新语句。

完成时间 finish_time 不在 SET 中，因此保留原值。正常待接单订单的完成时间为 null，拒单后依然为 null。订单金额、支付状态和支付时间等也保持原值。

文档中的支付是模拟支付，5.4 未定义退款流程。本次不增加退款或支付状态改写；已支付但仍待接单的订单也按原状态规则处理。

## 6. 为什么并发时不会同时接单和拒单成功

两个请求都在事务中先锁门店、再锁订单。先得到锁的请求完成状态变更并提交后，后一个请求才能继续读到新状态。

- 拒单先成功：状态变为 4，接单读取到 4 后拒绝。
- 接单先成功：状态变为 2，拒单读取到 2 后拒绝。
- 两个请求同时拒单：只有一次成功，后一个不能覆盖第一次保存的原因和时间。

SQL 中的原状态条件继续约束数据库写入。与前面一致，采用门店锁也意味着使用该锁的同门店写操作会相互等待。

## 7. 与 5.3 的对照及学习重点

你写 5.3 时已经用对了路径参数、Long、公共权限检查，以及订单 ID、门店、原状态三个 SQL 条件。这次继续沿用这些部分。

| 对照点 | 5.3 完成订单 | 5.4 拒单 |
| --- | --- | --- |
| 请求参数 | 路径 ID | 路径 ID + JSON 原因 |
| 原状态 | 2 已接单 | 1 待接单 |
| 目标状态 | 3 已完成 | 4 已取消 |
| 需要记录 | 完成时间、更新时间 | 拒单原因、更新时间 |
| 完成时间处理 | 写入服务端时间 | 保持原值 |
| 事务、归属、行数检查 | 都需要 | 都需要 |

5.3 初稿的问题是完成时间独立更新时漏了 WHERE，以及更新为 0 行时仍走成功返回。这次通过一次 SQL 更新和严格检查行数处理，写其他状态接口时也可以套用这套检查思路。

本次 5.4 由助手从已有基础补齐，没有用户的新初稿可独立评价。学习时可重点尝试解释：为什么状态必须是 1、为什么读取请求体但不能信任其中的 storeId、为什么拒单不能写 finish_time。

## 8. 验证范围

新增测试使用独立 H2 数据库执行真实 Mapper SQL，模拟 Redis，不连接或修改业务 MySQL、Redis。覆盖：JSON 参数、原因必填与长度、首尾空白、路径和门店不可被覆盖、四种状态、重复拒单、跨店与管理员权限、大 ID、其他订单不受影响、实际更新后的事务回滚，以及并发拒单、接单与拒单竞争。

H2 的测试结果不代表已经验证真实 MySQL 的锁等待和线上运行情况，后续联调应继续使用隔离测试数据。
