# 9.4 删除购物车项实现讲解

本接口为 `DELETE /app/cart/{id}`，删除当前登录顾客购物车中的某一条记录。`id` 是购物车项主键，不是菜品 ID。

## 一、与上一接口的区别

| 接口 | 请求数据 | 定位方式 | 操作结果 |
| --- | --- | --- | --- |
| 9.3 修改数量 | JSON 中 dishId、quantity | 当前用户 + 菜品 ID | 设置目标数量 |
| 9.4 删除条目 | 路径中的 id | 当前用户 + 购物车项 ID | 删除这一条购物车记录 |

例如 9.1 返回：

```json
{"id":1001,"dishId":101,"name":"宫保鸡丁","quantity":2}
```

删除这一项时，应请求：

```http
DELETE /app/cart/1001
Authorization: 用户登录返回的完整 token
```

购物车记录 1001 被删除，菜品 101 仍然保留在菜单中。同一用户的其他条目、其他用户购买的同一道菜，都不受影响。

可以把 9.4 当作 9.3 的延伸：继续复用当前用户身份获取，重点比较参数来源、定位条件与删除行为。

## 二、Controller：从路径接收购物车项 ID

```java
@DeleteMapping("/{id}")
public Result delete(@PathVariable("id") Long id) {
    cartService.delete(id);
    return Result.success();
}
```

类上的 `/app/cart` 与方法路径组合成完整地址。`@PathVariable` 读取路径中的数字，不需要 JSON 请求体，也不要求数量或门店参数。

## 三、Service：读取身份、检查 ID、执行删除

```java
@Transactional
public void delete(Long id) {
    Long userId = UserContextUtil.getCurrentUserId();
    if (id == null || id < 1) {
        throw new BizException("请选择有效的购物车项ID");
    }
    int rows = cartMapper.deleteByIdAndUserId(id, userId);
    if (rows != 0 && rows != 1) {
        throw new BizException("删除购物车项失败，请重试");
    }
}
```

userId 来自拦截器验证后保存的 ThreadLocal 身份，前端无法通过额外参数选择其他用户。

不查询菜品上下架状态，因为删除的对象是已有购物车项；下架条目也应该可以移除。

## 四、Mapper：在同一条 DELETE 中限制归属

```java
@Delete("delete from t_cart where id = #{id} and user_id = #{userId}")
int deleteByIdAndUserId(@Param("id") Long id, @Param("userId") Long userId);
```

两个条件必须同时成立：

```text
购物车项主键等于传入 id
并且
这条记录属于当前用户
```

因此，当前用户请求其他人的购物车项 ID 时，数据库不会删除那条记录。SQL 本身限定范围，不依赖前端自觉，也不需要先查询再删除。

不要复用已有的 `deleteByDishIdAndStoreId`。那个方法服务于管理端删除菜品，需要清理该菜品在店内所有用户的引用；顾客移除一项时必须只删除本人条目。

## 五、为什么删除 0 行也成功

9.4 文档只规定成功响应，未规定不存在条目的失败格式。本次选择重复删除保持成功：

- 删除 1 行：本次确实移除了一个自己的条目。
- 删除 0 行：该 ID 已不存在，或者不属于当前用户，不做任何修改。

这样网络重试、连续点击删除都能得到成功，同时不向调用者区分“其他人的条目存在”与“这个 ID 不存在”。成功表示删除操作在当前用户范围内完成，并不表示调用者拥有过任意传入 ID。

## 六、事务与并发

单条 DELETE 已经是原子操作，会对实际删除的行取得数据库锁。这里使用事务，还可以在受影响行数异常时抛出业务错误并回滚。

数量修改和加购也会操作同一购物车记录，数据库行锁协调先后顺序：

```text
先改数量，再删除 → 整条记录被删除
先删除，再改数量 → 修改发现条目不存在，不会重新创建
先加购，再删除 → 加购后的条目被删除
先删除，再加购 → 加购创建新的购物车项，使用新主键
```

最后一种情况下，重试旧主键的删除不会把后来新增的购物车项删除。这也是必须区分购物车项 ID 和菜品 ID 的原因之一。

购物车删除不会修改菜单数据，因此不清理菜品列表缓存。9.1 查询购物车会直接读取数据库，删除结果会在下一次列表查询中体现。

## 七、完整调用链与验证范围

```text
DELETE /app/cart/1001
→ 登录拦截器验证顾客 token
→ Controller 从路径取得 1001
→ Service 从 ThreadLocal 取得当前用户 ID
→ Mapper 按 id + user_id 删除
→ 接受 0 或 1 行结果，提交事务
→ Controller 返回成功，data 为 null
→ 拦截器清理 ThreadLocal
```

测试使用独立 H2 执行真实 SQL，Redis 使用带状态的模拟对象。覆盖本人删除、其他用户隔离、重复删除、下架条目、购物车 ID 与菜品 ID 的区别、参数边界、异常回滚、并发重复删除及与加购和改数量的操作顺序。

此验证不等同于真实 MySQL、Redis 环境联调。
