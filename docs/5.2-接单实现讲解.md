# 5.2 接单实现讲解

## 1. 请求和状态规则

```http
PUT /admin/order/accept/1
Authorization: 登录获得的原始token
```

将示例中的 1 替换为本店真实的待接单订单 ID。ID 来自路径，不需要查询字符串或 JSON 请求体，也不需要前端指定目标状态、门店。

文档规定唯一允许的状态流转为：`1 待接单 → 2 已接单`。

| 当前状态 | 接单结果 |
| --- | --- |
| 1 待接单 | 更新为 2 |
| 2 已接单 | 拒绝重复接单 |
| 3 已完成 | 拒绝接单 |
| 4 已取消 | 拒绝接单 |

成功返回 `{"code":0,"message":"操作成功","data":null}`；状态不允许时返回 `{"code":1,"message":"当前订单状态不允许接单","data":null}`。

## 2. Controller：参数来自路径

```java
@PutMapping("/accept/{id}")
public Result accept(@PathVariable("id") Long id) {
    orderService.accept(id);
    return Result.success();
}
```

`@PathVariable` 对应 `/accept/1`；`@RequestParam` 对应 `?id=1`。你原来的路径里有 `{id}`，方法却使用 `@RequestParam`，按文档请求时会被认为缺少查询参数。

订单 ID 对应数据库 BIGINT，各层改为 Long。请求中的 `?id=其他订单`、`?storeId=其他门店`、`?status=4` 都不会改变路径目标、登录门店或接单目标状态。

## 3. Service：身份、归属、状态三个方面都检查

`OrderServiceimpl.accept()` 使用 `@Transactional`，依次执行：

1. 通过 `AdminContextUtil.getCurrentAdminStoreId()` 验证登录、管理员角色、门店绑定。
2. 检查订单 ID 非 null 且大于 0。
3. 先查询并锁定当前门店，与整店删除遵循相同锁顺序。
4. 按订单 ID 和当前门店查询并锁定订单；不存在或不属于本店则拒绝。
5. 要求当前订单状态为 1，其余状态按文档提示拒绝。
6. 执行带原状态条件的更新，检查影响行数为 1，成功后提交事务。

只改变 status、update_time，金额、支付状态、下单时间、完成时间、备注、取餐信息等保持原值。接单时不填写 finish_time，完成时间留到 5.3 完成订单时设置。

## 4. Mapper：方法名字不会自动给数据库加锁

查询语句：

```java
@Select("select * from t_orders where id = #{id} and store_id = #{storeId} for update")
Order findByIdAndStoreIdForUpdate(@Param("id") Long id, @Param("storeId") Long storeId);
```

你原来的方法虽然叫 `findByIdforUpdate`，注解 SQL 中却没有 `for update`。数据库执行的是 SQL，方法名字本身不产生锁。

现在查询与后续更新处于同一事务，门店、订单行上的锁到事务提交或回滚时释放。其他使用相同门店锁的写操作会等待，因此同一门店的这些写操作会串行协调。

更新语句：

```java
@Update("update t_orders set status = 2, update_time = #{updateTime} " +
        "where id = #{id} and store_id = #{storeId} and status = 1")
int accept(@Param("id") Long id,
           @Param("storeId") Long storeId,
           @Param("updateTime") LocalDateTime updateTime);
```

WHERE 中的三个条件分别限制目标订单、本店归属、允许流转的原状态。Java 先检查状态用于给出业务提示，SQL 再限定原状态，避免覆盖已改变的订单状态。

调用与判断分开写：

```java
int rows = orderMapper.accept(id, storeId, LocalDateTime.now());
if (rows != 1) {
    throw new BizException("当前订单状态不允许接单");
}
```

## 5. 重复请求和并发请求

首次接单后订单变成 2。再次接单会返回业务错误，这是按 5.2“其余状态一律拒绝”的规定实现的，与 4.4 重复设置同一个上下架状态仍成功的规则不同。

两个请求同时接同一订单时，前一个获取锁后完成 1→2，后一个等待锁释放后读到状态 2 并拒绝。测试使用两个线程、独立数据库事务验证只有一次成功。

订单分页当前直接查数据库，后续查询能看到提交后的状态，接单无需调用菜品列表缓存清理方法。

## 6. 与上次 5.1 相比

这次你已经主动根据文档检查待接单状态，SQL 也写出了 WHERE id，开始按“先查订单、判断状态、再更新”的流程组织写操作。这些部分是你原代码中已经完成的。

需要继续固定复用的是 5.1 已有的门店隔离：读接口和写接口都必须从登录身份确定范围。路径参数绑定、Long 类型，以及行锁和事务配合也仍需逐项自查。本次补上这些保护，并在 UPDATE 中增加门店、原状态条件。

新增测试使用独立 H2 数据库执行真实 SQL、模拟 Redis，覆盖参数绑定、四种订单状态、重复请求、跨店与顾客权限限制、大 ID、事务回滚和并发接单。真实 MySQL、Redis 联调尚未覆盖。
