# 6.1 今日数据看板实现讲解

## 1. 把接口理解成“店长查今天的账本”

前端发起：

```http
GET /admin/stats/today
Authorization: 登录获得的原始token
```

不需要请求体、分页参数或门店 ID。服务端从登录信息识别当前门店，去订单表数数量、加金额，把五个数字返回给前端。

可以把各层理解成：

- Controller 是接待员，收到“查询今日报表”的请求并返回结果。
- Service 是店长，决定查哪家店、哪一天、哪些订单应该算进去。
- Mapper 是查账员，根据 SQL 到数据库数订单、加金额。
- TodayStatsVO 是报表表格，存放查出来的五个数字。

## 2. 先用五笔订单把统计口径说清楚

假设今天本店相关的订单如下，所有金额单位为元：

| 订单 | 下单日期 | 当前状态 | 完成日期 | 金额 |
| --- | --- | --- | --- | --- |
| A | 今天 | 1 待接单 | 无 | 10.00 |
| B | 今天 | 2 已接单 | 无 | 20.00 |
| C | 昨天 | 3 已完成 | 今天 | 30.00 |
| D | 今天 | 3 已完成 | 今天 | 40.00 |
| E | 今天 | 4 已取消 | 无 | 50.00 |

本次实现的结果：

```json
{
  "code": 0,
  "message": "操作成功",
  "data": {
    "orderCount": 4,
    "pendingCount": 1,
    "finishedCount": 1,
    "canceledCount": 1,
    "turnover": 70.00
  }
}
```

原因：

1. 今天下单的是 A、B、D、E，所以总数为 4。
2. 这四笔中，待接单、已完成、已取消各 1 笔。
3. B 已接单，计入总数，但文档未要求单独返回 acceptedCount。因此三个分类数量之和不一定等于总数。
4. 今天完成的是 C、D，所以营业额是 30.00 + 40.00 = 70.00。

文档明确了营业额要按完成时间统计，但没有进一步细化数量指标的时间口径。本实现沿用前面讨论的约定：数量按“今天下单、当前状态”统计，营业额按“今天完成且状态为 3”统计。这意味着 finishedCount 和 turnover 可以来自不同的订单集合。

## 3. Controller：把查出的报表放进响应 data

位置：`com.wys.orderingserver.controller.admin.StatsController`。

你的 `@RestController`、类上的 `@RequestMapping("/admin/stats/today")` 和方法上的 `@GetMapping` 原本就能组成正确路径，本次保留。

```java
public Result<TodayStatsVO> getStats() {
    TodayStatsVO stats = statsService.getStats();
    return Result.success(stats);
}
```

原来只有 `statsService.getStats()`，Controller 却声明返回 Result，因此缺少返回内容。现在 Service 返回统计对象，Controller 用 `Result.success(stats)` 包装，stats 就是 JSON 中的 data。

这是查询接口，需要带回数据；前面的接单、拒单成功时只需 `Result.success()`，data 可以为空。

## 4. Service：确定门店和“今天”

位置：`com.wys.orderingserver.service.StatsService` 和 `service.impl.StatsServiceimpl`。

Service 接口从 void 改为：

```java
TodayStatsVO getStats();
```

void 表示不返回结果，查询看板需要返回五项数字，所以这里使用 TodayStatsVO。

先取得门店：

```java
Long storeId = AdminContextUtil.getCurrentAdminStoreId();
```

这个公共方法已经检查登录、管理员角色和有效门店绑定；缺少门店 ID 会抛异常，因此不需要再写 `if (storeId == null)`。它检查的是登录信息中的门店绑定，不等于额外查询数据库确认门店记录存在。统计 SQL 始终限定该门店，查询范围没有订单时返回零。

随后计算时间边界：

```java
LocalDate today = LocalDate.now(ZoneId.of("Asia/Shanghai"));
LocalDateTime beginTime = today.atStartOfDay();
LocalDateTime endTime = today.plusDays(1).atStartOfDay();
```

假设今天为 2026-10-18：

- beginTime 是 2026-10-18 00:00:00。
- endTime 是 2026-10-19 00:00:00。
- 查询包含 beginTime，不包含 endTime。

SQL 写成 `时间 >= beginTime AND 时间 < endTime`，今天最后一秒中的小数部分也不会遗漏，明天零点也不会误算进今天。五次查询复用同一次计算的边界，避免跨零点时每项统计使用了不同日期。业务日期明确采用上海时区。

## 5. Mapper：两个方法完成五项统计

统计对象来自订单表，所以在已有 OrderMapper 中追加两个方法，继续使用注解加字符串拼接的风格。

### 5.1 数数量：COUNT

```sql
SELECT COUNT(*) FROM t_orders
WHERE store_id = #{storeId}
  AND create_time >= #{beginTime}
  AND create_time < #{endTime}
  AND (#{status} IS NULL OR status = #{status})
```

COUNT(*) 可以理解成“有几笔符合条件的订单”。一个 SQL 通过不同 status 参数复用四次：

| status 参数 | 统计内容 | 放入字段 |
| --- | --- | --- |
| null | 不限制订单状态 | orderCount |
| 1 | 待接单 | pendingCount |
| 3 | 已完成 | finishedCount |
| 4 | 已取消 | canceledCount |

这里 null 只表示不限制状态。`store_id = #{storeId}` 始终存在，不能因为统计总数就取消门店限制。

### 5.2 加金额：SUM

```sql
SELECT COALESCE(SUM(amount), 0) FROM t_orders
WHERE store_id = #{storeId}
  AND status = 3
  AND finish_time >= #{beginTime}
  AND finish_time < #{endTime}
```

SUM(amount) 可以理解成“把符合条件订单的金额加起来”。只取已完成、今天完成、本门店的订单。

没有符合条件的订单时，SUM 原本可能得到 null；COALESCE 将它替换为 0。金额使用 BigDecimal，并在 Service 中统一保留两位小数。

这里不按 pay_time、create_time 或 update_time 算营业额，也不额外改写支付状态。5.3 完成订单时写入的 finish_time，正是在这里发挥作用。

## 6. 装进 VO，然后沿调用链返回

```java
TodayStatsVO stats = new TodayStatsVO();
stats.setOrderCount(orderMapper.countByCreateTime(storeId, null, beginTime, endTime));
stats.setPendingCount(orderMapper.countByCreateTime(storeId, 1, beginTime, endTime));
stats.setFinishedCount(orderMapper.countByCreateTime(storeId, 3, beginTime, endTime));
stats.setCanceledCount(orderMapper.countByCreateTime(storeId, 4, beginTime, endTime));
stats.setTurnover(orderMapper.sumTurnover(storeId, beginTime, endTime).setScale(2));
return stats;
```

前四行调用的是同一个数量方法，只是状态不同；最后一行调用金额方法。查询结果填入 VO，返回 Controller，再由 Spring 转成 JSON。

接口不需要分页，也没有在 Java 中取出全部订单再循环统计。

## 7. 为什么查询也加了事务

```java
@Transactional(readOnly = true, isolation = Isolation.REPEATABLE_READ)
```

五项数据需要多次查询。如果统计总数之后，有其他请求完成了订单，而状态数量、营业额读到了更新后的数据，一张报表就可能混用两个时刻的结果。

可以理解成“先对账本拍一张照片，再根据同一张照片数数量、加金额”。本项目 MySQL InnoDB 下的可重复读事务用于让这些普通 SELECT 基于一致快照；readOnly 表达只读意图。这与 5.2、5.3、5.4 更新时使用 FOR UPDATE 锁定待修改记录的用途不同，本接口不使用 FOR UPDATE。

## 8. 和你前面写法的对照

这次检查前，你已经写出了正确的路由、Controller 调 Service、Service 注入 OrderMapper，并主动调用公共权限方法。和早期需要反复确认注解、门店从哪里来的阶段相比，分层的接线更完整了。

需要继续练习的是“查询结果如何一路返回”：Service 不能是 void，Controller 不能只调用方法却不 return。统计查询的新知识则是时间边界、COUNT、SUM，以及把不同查询结果装进 VO。

本次补齐统计 SQL、返回链路和一致性保护；这些是助手完成的部分。理解后可以尝试自己口述五笔示例订单分别会计入哪些字段，确认掌握了统计口径。

## 9. 验证范围

使用独立 H2 数据库执行真实 SQL，Redis 通过 Mockito 模拟，未连接或修改业务 MySQL、Redis。测试覆盖五个响应字段、跨店限制、空数据返回零、下单与完成时间的不同口径、零点和最后小数秒、BigDecimal 金额、上海业务日期、权限校验，以及其他事务完成订单时本次统计仍保持同一快照。

真实 MySQL 的运行和隔离行为仍需在联调环境验证，当前不能据此声称已经完成业务环境联调。
