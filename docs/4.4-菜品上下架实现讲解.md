# 4.4 菜品上下架实现讲解

## 1. 请求格式与参数来源

```http
PUT /admin/dish/status/6?status=0
Authorization: 登录获得的原始token
```

- 路径里的 `6` 是菜品 ID，用 `@PathVariable("id") Long id` 接收。
- 查询字符串里的 `status=0` 是目标状态，用 `@RequestParam("status") Integer status` 接收。
- `status=1` 表示上架，`status=0` 表示下架。这是设置目标状态，不是每次请求都取反。
- 请求不需要 JSON 体，也不需要前端传门店 ID。

成功响应与文档一致：

```json
{"code":0,"message":"操作成功","data":null}
```

## 2. Controller → Service → Mapper 的运行过程

Controller 绑定路径、查询参数后，调用 `DishService.updateDishStatus(id, status)`。

Service 在一个 `@Transactional` 事务中依次处理：

1. 调用 `AdminContextUtil.getCurrentAdminStoreId()`，检查登录、管理员身份和门店绑定。
2. 校验 ID 大于 0、状态非 null 且只能为 0 或 1。
3. 先查询并锁定当前门店，与其他门店写接口使用相同的加锁顺序。
4. 按“菜品 ID + 当前门店 ID”查询并锁定目标菜品，拒绝不存在和属于其他门店的菜品。
5. 当前状态不同于目标状态时，更新状态、更新时间，并检查影响行数为 1。
6. 注册提交后清缓存。数据库成功提交后，复用 `clearDishCacheAfterCommit()` 清理本店菜品列表缓存。

相同目标状态重复提交，仍然返回成功，保留原更新时间，并执行提交后的缓存清理。这使重试不会把已经下架的菜品重新上架。

## 3. Mapper 的查询与更新

```java
@Select("select * from t_dish where id = #{id} and store_id = #{storeId} for update")
Dish findByIdAndStoreIdForUpdate(@Param("id") Long id, @Param("storeId") Long storeId);

@Update("update t_dish set status = #{status}, update_time = #{updateTime} " +
        "where id = #{id} and store_id = #{storeId}")
int updateDishStatus(@Param("id") Long id,
                     @Param("status") Integer status,
                     @Param("storeId") Long storeId,
                     @Param("updateTime") LocalDateTime updateTime);
```

查询和更新都限制门店：查询确定当前门店有这道菜，更新 SQL 再限定一次操作范围。方法有多个参数，所以使用 `@Param` 明确 SQL 占位符名称。菜品 ID 对应数据库 BIGINT，各层统一使用 Long。

只更新状态和更新时间，菜名、价格、分类、图片、描述、排序、创建时间及其他菜品的数据保持不变。

## 4. 原代码中的缺陷

你原来的更新语句：

```sql
update t_dish set status = #{status}
```

没有 WHERE，会尝试更新整张表。Service 即使查询过某道菜，查询结果也不会自动变成下一条 UPDATE 的条件。WHERE 必须写在 UPDATE 语句里。

原来的 `findById(id)` 只说明菜品存在，没有证明它属于当前门店，因此改为同时按 ID、门店查询。

原来的上下架方法缺少 `@Transactional`，会使 `for update` 无法覆盖后续业务，调用事务回调注册时还可能出现“事务同步未激活”的异常。数据库更新可能已经提交，接口却报告失败。现在事务覆盖查询、更新、回调注册，失败时回滚；缓存只在成功提交后清理。

状态参数也加入了 null 检查，避免 Service 被直接调用时自动拆箱产生空指针异常。

## 5. 缓存范围与当前边界

复用 4.3 的逻辑，只清理 `dish:{当前门店ID}:*`，不会清理其他门店和登录令牌。回滚时不清理缓存。

用户端缓存读取、重建仍按顺序留到 8.3，图片上传留到 11.1。Redis 清理失败会记录错误日志，数据库修改仍成功；当前没有持久化重试任务。

## 6. 与上次 4.3 相比

你这次正确区分了路径参数和查询参数，增加了菜品存在性检查，也主动复用提交后缓存清理方法。这些处理已经进入了你的实现步骤。

WHERE 条件和事务仍出现遗漏，说明这两项还需要形成固定检查习惯：每写一条 UPDATE，先检查“改哪些字段、改哪一条记录、是否限定门店”；使用 `for update` 或提交回调时，检查调用它的 Service 方法是否有事务。

验证使用独立 H2 内存数据库和模拟 Redis，覆盖上下架、重复请求、跨店访问、大 ID、数据库回滚和缓存清理时机。真实 MySQL、Redis 联调尚未覆盖。
