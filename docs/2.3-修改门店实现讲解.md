# 2.3 修改门店实现讲解

## 1. 请求示例与权限

```http
PUT /admin/store
Authorization: 登录获得的原始token
Content-Type: application/json

{"id":1,"name":"望京旗舰店","notice":"工作日午市9折","status":1}
```

ID 来自请求体，需要替换为实际目标门店 ID；名称也是必填。地址、电话、营业时间、公告、营业状态为选填。

文档 2.3 没有限制“仅超管修改”，因此结合通用权限说明和现有门店查询规则实现：

| 身份 | 可以修改的门店 |
| --- | --- |
| 超级管理员 | 任意存在的门店，不要求超管自己绑定门店 |
| 已绑定门店的普通管理员 | 只能修改自己绑定的门店 |
| 未绑定门店的普通管理员、顾客、其他角色 | 拒绝 |

登录拦截器仍负责 token、Redis 和员工有效性检查。本接口继续复用 AdminContextUtil，不手写一套 role 解析。

## 2. 你已经写好的部分与这次补齐的部分

检查前，你已经写出了正确的 `@PutMapping`、`@RequestBody Store store`，Controller 调用了 Service，并返回 `Result.success()`；Service 接口也声明了 `updateStore(Store store)`。

这比 6.1 初稿中“调用 Service 后没有 return”更完整。本次保留调用链和方法名。

当时实现方法为空，Mapper 也没有更新 SQL，所以请求虽然返回成功，数据库却不会改变。本次补齐权限、校验、事务和 SQL，并验证数据库确实改变。

## 3. Controller：接收 JSON，触发修改分组校验

```java
@PutMapping
public Result updateStore(@Validated(Store.Update.class) @RequestBody Store store) {
    storeService.updateStore(store);
    return Result.success();
}
```

类上的路径为 `/admin/store`，与 PUT 方法共同构成文档要求的接口。这里的 ID 是 JSON 中的 id，所以不使用 @PathVariable。

Store 的修改分组要求 ID 不为 null；名称使用 @NotBlank，拒绝缺失、空字符串和纯空白。Update 分组继承 Default，所以名称的默认分组约束也会执行。

字段约束和报错信息：

```java
@NotNull(groups = Update.class, message = "门店ID不能为空")
private Long id;

@NotBlank(message = "门店名称不能为空")
private String name;
```

## 4. Service：决定是否允许修改，并准备更新数据

`StoreServiceimpl.updateStore()` 添加了 @Transactional，按下面顺序运行：

1. `AdminContextUtil.isSuperAdmin()` 检查当前身份是管理员，并确定是否超管。
2. 检查 Store、ID 非 null，且 ID 大于 0。
3. 普通管理员通过公共方法取得 JWT 门店 ID，必须与请求目标 ID 相同；然后把登录门店 ID 设为真正传入 SQL 的目标。
4. 检查名称非空白，去掉首尾空白。
5. 检查字段长度、可选 status 只能为 0 或 1。
6. 使用 findByIdForUpdate 查询并锁定门店，门店不存在则拒绝。
7. 使用服务端当前时间设置 updateTime，执行 Mapper，要求影响行数等于 1。

例如管理员属于门店 1，请求中写 id=2 时，会返回“只能修改当前门店的信息”，不会更新门店 2。超管则允许指定 id=2。

这些 Service 检查也覆盖直接调用业务方法的情况，不只依赖 Controller 校验。

长度上限来自 ordering-ddl.sql，按 Unicode 字符数检查：

| 字段 | 上限 |
| --- | --- |
| name | 100 |
| address | 255 |
| phone | 20 |
| notice | 500 |

电话没有额外限制为 11 位手机号，因为门店电话也可以是座机。营业时间沿用 HH:mm:ss 格式，也允许晚上营业、次日凌晨结束的跨天时间安排。

## 5. Mapper：有 WHERE 的更新，未传字段保留原值

保持项目已有的注解加字符串拼接风格：

```java
@Update("update t_store set name = #{name}, " +
        "address = coalesce(#{address}, address), phone = coalesce(#{phone}, phone), " +
        "open_time = coalesce(#{openTime}, open_time), close_time = coalesce(#{closeTime}, close_time), " +
        "notice = coalesce(#{notice}, notice), status = coalesce(#{status}, status), " +
        "update_time = #{updateTime} where id = #{id}")
int updateStore(Store store);
```

`WHERE id = #{id}` 把更新限定为一条门店记录。门店表的主键 ID 本身就是门店范围；权限检查已经决定了这个 ID 是否允许操作。

例如：

```sql
notice = COALESCE(#{notice}, notice)
```

可以理解为：“传了新公告就用新公告，传入 null 就沿用数据库中的旧公告”。

| 选填字段的传法 | 效果 |
| --- | --- |
| 没传该字段 | 保留原值 |
| 显式传 null | 保留原值 |
| 字符串字段传空字符串 | 地址、电话、公告可清空 |
| status 传 0 | 改为打烊 |
| status 传 1 | 改为营业中 |

修改没有套用新增默认值：不传 status 时，原来打烊的门店不会被自动改成营业中。name 必填，不能用空字符串清空；时间字段不支持通过空字符串清空。

SQL 不更新 id 或 create_time；update_time 始终由服务端设置。创建时间和更新时间原有的 JSON 只读标记继续生效，客户端不能伪造这些时间。

## 6. 为什么要事务和影响行数检查

锁定门店与随后的更新放在同一个事务，门店行锁到提交或回滚时才释放。这样与整店删除等使用相同行锁的操作协调，避免查询到门店存在后，又被并发删除。

调用与结果判断展开写：

```java
int rows = storeMapper.updateStore(store);
if (rows != 1) {
    throw new BizException("门店修改失败，请刷新后重试");
}
```

返回值表示数据库更新的行数。只应更新目标门店一行；如果没有更新成功，就抛出异常，不让 Controller 返回成功。运行时异常触发事务回滚。

正常返回：

```json
{"code":0,"message":"操作成功","data":null}
```

## 7. 学习时可以这样串起来

假设你要把本店名称改为“望京旗舰店”：

1. 前端提交门店 ID 和新名称。
2. Controller 把 JSON 转成 Store，检查必填项。
3. Service 确认你有权修改该店，检查字段，填入更新时间。
4. Mapper 根据门店 ID 更新名称，其他没传的字段保持原样。
5. 数据库返回影响行数 1，事务提交，Controller 返回成功。
6. 再调用已有的 2.1 分页查询，即可看到新名称。

这次你自己写对的是入口、参数绑定、接口声明和成功返回；本次由助手补齐的是实际业务与数据库更新。理解后可以对照 3.3 修改分类、4.3 修改菜品，找出它们共同的“权限 → 参数 → 归属 → 更新 → 检查结果”流程。

## 8. 测试范围

新增集成测试使用独立 H2 数据库执行真实 Mapper SQL，模拟 Redis，不访问业务 MySQL、Redis。

验证超管和普通管理员权限、跨店拦截、必填与长度边界、空值保留和空字符串清空、时间格式、长整型 ID、时间不可伪造、其他门店和员工不受影响、分页查询看到修改结果、真实写入后的异常回滚，以及并发修改不同选填字段时都能保留。

测试用表的 name、notice 长度仅在新测试的独立数据库中调整为建表文档的 100、500，没有修改现有业务数据库或其他测试库。
