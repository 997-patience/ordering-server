# 5.3 完成订单实现讲解

## 1. 文档要求与请求方式

```http
PUT /admin/order/complete/102
Authorization: 登录获得的原始token
```

把 102 换成当前门店实际已接单的订单 ID。请求不需要 JSON 请求体，也不需要提交门店 ID、目标状态或完成时间。

唯一允许的流转是 `2 已接单 → 3 已完成`，并由服务端记录完成时间。

| 当前状态 | 本接口的处理 |
| --- | --- |
| 1 待接单 | 拒绝，应先接单 |
| 2 已接单 | 更新为 3，同时记录完成时间和更新时间 |
| 3 已完成 | 拒绝重复完成，不改写已有完成时间 |
| 4 已取消 | 拒绝完成 |

成功返回 `{"code":0,"message":"操作成功","data":null}`。状态不允许时返回 `{"code":1,"message":"当前订单状态不能完成","data":null}`，业务异常由项目的全局异常处理器转换成 JSON。

文档未要求额外校验支付状态，因此本接口没有增加“必须已支付”的条件，也不改变支付状态或支付时间。

## 3. 原来的完成时间更新有什么问题

你原先分成两个 Mapper 调用：

```java
int rows = orderMapper.complete(id, storeId, updateTime);
if (rows >= 1) {
    orderMapper.finish(updateTime);
}
```

第一条 SQL 只更新目标订单状态；第二条 SQL 却是：

```sql
UPDATE t_orders SET finish_time = #{updateTime}
```

这条 SQL 没有 WHERE，执行时会把 t_orders 中所有订单的完成时间都设置为同一个时间，包括其他门店、未完成订单和历史已完成订单。

前一条 SQL 的 WHERE 条件不会传给后一条。每条 SQL 都必须独立保证自己的操作范围。原来的 `if (rows >= 1)` 只决定是否调用 finish，不会限制 finish 更新哪些记录。

另一个问题是：`rows = 0` 时没有抛出异常，Service 会正常返回，Controller 仍然返回成功，形成“数据库没更新，接口却提示成功”。

## 4. Controller → Service：按顺序执行检查

Controller 和 Service 接口签名原本正确，无需改动。请求进入 `OrderServiceimpl.complete()` 后执行：

1. 从 ThreadLocal 中的登录信息获取当前管理员门店，不能用前端的 storeId 覆盖。
2. 检查订单 ID 非 null 且大于 0。
3. 通过 `StoreMapper.findByIdForUpdate()` 查询并锁定门店。
4. 通过 `OrderMapper.findByIdAndStoreIdForUpdate()` 查询并锁定本店目标订单。
5. 不存在或不属于本门店则拒绝；当前状态不是 2 也拒绝。
6. 取一次服务端当前时间，调用 Mapper，检查影响行数恰好为 1。

方法添加了 `@Transactional`。正常结束后提交；抛出 BizException 或其他运行时异常时回滚。BizException 继承 RuntimeException，所以这里默认事务回滚规则就能生效。

`FOR UPDATE` 要与事务配合：查询获取的行锁需持续到后续写入结束，事务提交或回滚后释放。门店锁在前、订单锁在后，与接单、整店删除保持相同顺序，便于这些操作协调；同时也意味着使用相同门店锁的同店写操作会相互等待。

## 5. Mapper → 数据库：用一条 SQL 完成写入

```java
@Update("update t_orders set status = 3, update_time = #{completeTime}, finish_time = #{completeTime} " +
        "where id = #{id} and store_id = #{storeId} and status = 2")
int complete(@Param("id") Long id,
             @Param("storeId") Long storeId,
             @Param("completeTime") LocalDateTime completeTime);
```

参数来源：

| 参数 | 来源 | 用途 |
| --- | --- | --- |
| id | URL 路径 | 指定目标订单 |
| storeId | 已认证登录信息，经公共工具检查 | 限制为当前门店 |
| completeTime | Service 中 LocalDateTime.now() | 同时写入完成时间和更新时间 |

SET 中的三个字段在同一条 SQL 中更新，避免出现“状态已完成，但完成时间没有写入”的分步结果。

WHERE 的三个条件限制目标订单、门店归属和原状态。Java 中的状态检查方便给出提示，SQL 中的状态条件则继续约束真正的数据库写入。

Service 使用展开写法：

```java
LocalDateTime completeTime = LocalDateTime.now();
int rows = orderMapper.complete(id, storeId, completeTime);
if (rows != 1) {
    throw new BizException("当前订单状态不能完成");
}
```

只取一次当前时间，因此两个时间字段使用相同的值。`finishTime` 表示业务完成时刻，`updateTime` 表示本次修改时刻；完成订单这一操作发生时两者相同，字段含义仍然不同。今日营业额后续应按 finish_time 统计，不应使用下单时间代替。

独立的 `finish()` 方法及其无条件更新 SQL 已移除。订单金额、支付信息、下单时间、备注、取餐信息不在 SET 中，因此不会被本接口改写。

## 6. 重复请求、并发与测试范围

完成后状态变为 3，再次完成会被拒绝，不会刷新 finish_time。当前已实现的接单接口同样拒绝状态为 3 的订单。后续拒单等状态修改也应遵守已完成订单不能再变更的规则。

两个请求同时完成同一订单时，先获取锁的请求完成 2→3 并提交，另一个请求等待后读到 3 并拒绝。影响行数检查防止更新未生效仍返回成功。

新增测试使用独立 H2 数据库执行真实 Mapper SQL，Redis 通过 Mockito 模拟。验证完成时间与更新时间一致、其他订单和其他门店全部字段不变、非法状态、重复完成、权限与归属、长整型 ID、SQL 条件保护、实际写入后的异常回滚，以及两个事务并发完成只有一次成功。

测试未连接业务 MySQL、Redis；真实 MySQL 的锁等待与线上运行情况仍需在联调环境验证。

以后写更新接口时，尤其自查两点：每一条 UPDATE 都有自己的 WHERE；数据库未更新时不能走成功返回。
