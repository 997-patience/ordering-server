# 4.5 删除菜品实现讲解

## 1. 接口与请求参数

```http
DELETE /admin/dish?id=8
Authorization: 登录获得的原始token
```

菜品 ID 来自查询字符串，通过 `@RequestParam("id") Long id` 接收。把示例中的 8 替换为当前门店待删除的菜品 ID，不需要 JSON 请求体，不需要前端传门店 ID。

成功响应：

```json
{"code":0,"message":"操作成功","data":null}
```

文档没有要求必须先下架，因此本实现允许删除当前门店的上架、下架菜品。不存在或属于其他门店的菜品会返回业务错误，不会影响其他数据。

## 2. Controller → Service → Mapper 的执行链

你已有的 Controller 接收 ID 后调用 `DishService.deleteDish(id)`。Service 在一个 `@Transactional` 事务中执行：

1. 获取当前管理员的门店 ID，并完成登录、角色、门店绑定检查。
2. 校验菜品 ID 非 null 且大于 0。
3. 先锁门店，再按“菜品 ID + 当前门店 ID”查询并锁定目标菜品，复用 4.4 的查询方法。
4. 删除当前门店购物车中对该菜品的引用，防止购物车保留无法购买的条目。
5. 删除目标菜品，检查影响行数必须为 1。
6. 注册事务提交后的缓存清理，提交成功后删除当前门店的菜品列表缓存。

购物车与菜品删除处于同一事务，任一步发生运行时异常时一起回滚，回滚时不清理缓存。

## 3. 两条 DELETE 为什么都有门店条件

CartMapper 中清理购物车：

```java
@Delete("delete from t_cart where dish_id = #{dishId} and store_id = #{storeId}")
int deleteByDishIdAndStoreId(@Param("dishId") Long dishId, @Param("storeId") Long storeId);
```

DishMapper 中删除菜品：

```java
@Delete("delete from t_dish where id = #{id} and store_id = #{storeId}")
int deleteDish(@Param("id") Long id, @Param("storeId") Long storeId);
```

所有占位符都使用参数绑定。门店 ID 来自登录信息，不能用请求参数替换。查询时检查归属，DELETE 再限定一次范围，避免误删其他门店的数据。

购物车中可能没有人添加过这道菜，因此购物车删除 0 行属于正常情况；目标菜品已经查询确认存在，菜品删除结果应为 1。

## 4. 这次把执行和判断分开写

结合你上次对“在 if 条件中调用 Mapper”的疑问，本次采用更直观的写法：

```java
cartMapper.deleteByDishIdAndStoreId(id, storeId);

int rows = dishMapper.deleteDish(id, storeId);
if (rows != 1) {
    throw new BizException("删除菜品失败，请重试");
}

clearDishCacheAfterCommit(storeId);
```

先执行 SQL 并获得结果，再根据结果判断是否成功，最后安排提交后清缓存。检查结果的 if 不负责执行删除，删除已经在赋值给 rows 的那一行发生。

## 5. 为什么保留历史订单

文档规定订单明细记录下单时的菜名、图片地址、单价、数量与金额快照。因此删除菜品只处理菜品表和购物车，不删除订单主表、订单明细，不清空历史明细中的 dish_id，也不删除图片文件。

例如当前菜品价格为 38 元，而旧订单快照单价为 35 元，删除菜品后旧订单仍保留 35 元。后续 10.3 订单详情应读取快照字段，按文档展示历史信息。

这种设计下，历史明细的 dish_id 用于溯源，订单展示不依赖对应菜品记录继续存在。原项目建表 SQL 没有给该字段配置指向菜品的外键。

## 6. 缓存处理和当前验证边界

复用 4.3、4.4 的 `clearDishCacheAfterCommit()`，数据库提交后清理 `dish:{当前门店ID}:*`。其他门店缓存及登录令牌不在清理范围内。

缓存读取、重建仍留到 8.3，图片上传留到 11.1。Redis 清理失败会记录日志，当前没有持久化重试任务。

## 7. 和你上一次实现的对比

这次你已经正确搭出 DELETE 入口，使用 Long 和查询参数接收 ID，并在 Service 中复用身份获取、ID 校验与门店检查。你提供的删除方法还没有执行删除 SQL，本次补齐了事务、目标菜品归属、购物车清理、删除 SQL 与提交后缓存处理。

接下来可以自己复述这一条链：删除谁 → 是否属于本店 → 哪些关联项需要清理 → 哪些历史数据要保留 → 什么时候清缓存。它比只写一条 DELETE 更完整。

测试使用独立 H2 内存数据库执行真实 SQL，模拟 Redis，覆盖跨店限制、购物车清理、历史订单快照保留、大 ID、事务回滚和缓存清理时机。真实 MySQL、Redis 联调尚未覆盖。
