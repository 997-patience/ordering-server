# 10.3 订单详情：检查结果与实现讲解

接口是 `GET /app/order/{id}`，查询当前顾客的一份订单，返回订单信息和全部菜品快照明细。

## 一、与你这次提交的代码对比

你已经写好了 `@GetMapping("/{id}")`、`@PathVariable("id")`，并串起 Controller → Service → Mapper。这与 10.2 的 queryString 分页参数有区别，你这次正确选择了路径参数。

还需要补齐四项：

| 原代码 | 问题 | 修改 |
| --- | --- | --- |
| `id < 0 || id == null` | 左侧先把 Long 拆箱，null 会先触发空指针；0 也未被拒绝 | `id == null || id < 1` |
| `t_order_detail where id=#{id}` | 请求传的是订单主键，这里却按明细主键查询 | 先查订单主表，再按 order_id 查全部明细 |
| 只有 id 条件 | 缺少本人订单范围限制 | 两次 SQL 都限定登录用户 |
| 返回 AppOrderListVO | 列表结构没有支付状态、备注、取消原因、完成时间和明细集合 | 使用详情 VO 和明细项 VO |

和 10.2 相比，你已经能根据参数来源选择注解，并完成新接口的分层调用。当前需要继续巩固的是：按 ID 查记录时，也要考虑登录用户的数据范围；关联表的主键与外键需要分清楚。

## 二、首先区分三个 ID

假设主表有一笔订单：

```text
t_orders.id = 100
```

它有两条明细：

| t_order_detail.id | t_order_detail.order_id | dish_id | dish_name |
| --- | --- | --- | --- |
| 800 | 100 | 101 | 宫保鸡丁 |
| 801 | 100 | 103 | 土豆丝 |

访问 `/app/order/100`，100 是订单主键。明细应当查询 `where order_id=100`，才能取回 800、801 两条明细。

如果写 `where id=100`，查的是主键为 100 的某一条明细，它可能不存在，也可能属于另一笔订单。

本次测试故意让某条明细主键与另一笔订单主键相同，验证不会发生这种混淆。

## 三、返回对象为什么拆成两个类

[AppOrderDetailVO](/D:/idea/Project/ordering-server/src/main/java/com/wys/orderingserver/pojo/AppOrderDetailVO.java:13) 表示一份完整订单详情，包含文档中的 14 个字段。

其中：

```java
private List<AppOrderDetailItemVO> details = new ArrayList<>();
```

用于保存这笔订单的多条菜品明细。

[AppOrderDetailItemVO](/D:/idea/Project/ordering-server/src/main/java/com/wys/orderingserver/pojo/AppOrderDetailItemVO.java:9) 表示其中一道菜，只包含：

```text
dishId、dishName、dishImage、dishPrice、quantity、amount
```

它们的关系类似：一张订单回执，下面列出多道菜。订单自己的 amount 是整单金额；每个 details 项中的 amount 是这道菜的小计。

pickupTime、createTime、finishTime 使用 `@JsonFormat` 保持文档中的日期时间格式，金额使用 BigDecimal。

## 四、Controller 如何接收参数

位置：[AppOrderController 第 27 行](/D:/idea/Project/ordering-server/src/main/java/com/wys/orderingserver/controller/app/AppOrderController.java:27)。

```java
@GetMapping("/{id}")
public Result<AppOrderDetailVO> getById(@PathVariable("id") Long id) {
    return Result.success(appOrderService.getById(id));
}
```

访问 `/app/order/100` 后，id 就是 100L。用户身份仍由原有登录拦截器校验，并存入本次请求的 ThreadLocal。

路径中的 id 决定要查哪一笔订单，登录信息中的 userId 决定调用者有没有权查看它。前端额外传 userId 或 storeId，不会改变这两个值的来源。

`/app/order/list` 仍然由 10.2 的固定路径处理，不会当成 Long 类型的订单 ID。

## 五、Service 如何组装完整详情

位置：[AppOrderServiceimpl 第 146 行](/D:/idea/Project/ordering-server/src/main/java/com/wys/orderingserver/service/impl/AppOrderServiceimpl.java:146)。

```java
@Transactional(readOnly = true, isolation = Isolation.REPEATABLE_READ)
public AppOrderDetailVO getById(Long id) {
    Long userId = UserContextUtil.getCurrentUserId();
    if (id == null || id < 1) {
        throw new BizException("请传入合法的订单ID");
    }
    AppOrderDetailVO order = orderMapper.getByIdAndUserId(id, userId);
    if (order == null) {
        throw new BizException("订单不存在或无权访问");
    }
    order.setDetails(orderDetailMapper.listByOrderIdAndUserId(id, userId));
    return order;
}
```

第 147 行取得登录用户。第 148 行先判 null，再进行数值比较；`||` 左侧为 true 时，右侧不会执行，从而避免空指针。

第 152 行查询当前用户的订单主信息。第 153 行处理查不到的情况：不存在和属于他人订单统一返回同一个错误，避免向调用者透露他人订单是否存在。

第 158 行查询全部明细，再调用 setter 把列表放入详情对象。这个 setter 只改变 Java 对象的返回内容，不会执行数据库 UPDATE。

假设主表查询返回订单 100，明细查询返回两道菜，那么 `setDetails()` 就把两道菜装进订单详情对象，Controller 最后包装成 Result 返回。

## 六、两条 SQL 分别查什么

主信息在 [OrderMapper 第 98 行](/D:/idea/Project/ordering-server/src/main/java/com/wys/orderingserver/mapper/OrderMapper.java:98)：

```sql
select o.id, o.order_no, o.store_id, s.name as store_name,
       o.amount, o.status, o.pay_status, o.remark,
       o.pickup_type, o.pickup_time, o.cancel_reason,
       o.create_time, o.finish_time
from t_orders o
left join t_store s on s.id = o.store_id
where o.id = #{id} and o.user_id = #{userId}
```

订单字段取自主表；门店名称关联门店表取得。订单主键与登录用户条件同时存在，所以不是“只要知道订单 ID 就能查看”。

明细在 [OrderDetailMapper 第 15 行](/D:/idea/Project/ordering-server/src/main/java/com/wys/orderingserver/mapper/OrderDetailMapper.java:15)：

```sql
select d.dish_id, d.dish_name, d.dish_image,
       d.dish_price, d.quantity, d.amount
from t_order_detail d
inner join t_orders o on o.id = d.order_id
where d.order_id = #{orderId} and o.user_id = #{userId}
order by d.id asc
```

`order_id` 用于取得本订单的全部明细。这里再关联订单主表核对 userId，是对明细查询本身的权限保护。即使单独调用这个 Mapper，也不会按他人的订单 ID 返回明细。

明细按照自身主键升序排列，让响应顺序稳定。没有明细时返回 `details: []`。

两个 Mapper 都继续使用注解 SQL 与字符串拼接，保持你要求的风格。

## 七、为什么历史菜品信息保持不变

明细 SQL 中的名称、图片、单价来自 `t_order_detail`，没有关联 `t_dish`。

比如下单时保存了“宫保鸡丁、图片 A、38 元”，以后商家把菜单改成“招牌鸡丁、图片 B、42 元”，详情仍读到原来保存的三个字段。即使当前菜品已下架或被删除，快照仍可展示。

金额也直接返回下单时保存的整单金额和明细小计，不根据当前菜单价格重新计算。

门店名称遵循文档的关联查询口径，展示当前门店表中的名称；它与菜品快照的口径不同。

## 八、两次查询为什么使用只读事务

主信息与明细是两条查询。如果查完主信息后，有其他事务删除订单及明细，后续读取就可能得到不一致的结果。

这里沿用 10.2 的可重复读方式，让同一次详情响应的普通查询使用同一快照。下一次请求会开启新的读取事务，看到新的数据状态。[MySQL 一致性读说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)

该详情接口读取本人订单，不要求绑定某家门店；待接单、已接单、已完成、已取消都可以查看。门店已打烊也不会隐藏本人的历史订单。
