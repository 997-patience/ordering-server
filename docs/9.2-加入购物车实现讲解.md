# 9.2 加入购物车实现讲解

请求是 `POST /app/cart`，JSON 中只需要菜品 ID 和本次新增数量：

```json
{"dishId":101,"quantity":2}
```

`userId` 从登录信息取得，`storeId` 根据菜品反查。重复加购时累加数量，而不是新建重复记录。

## 一、与你上次的实现相比

9.1 初写时只按门店查询，漏掉了当前用户条件。这次你已经主动调用 `UserContextUtil.getCurrentUserId()`，也正确写出了 `@RequestBody`、新增分组校验、菜品存在检查、下架检查，以及从菜品取得门店 ID。

这说明你已经开始把前面学过的身份获取和参数接收串到新的业务里。

本次主要补齐 Mapper，并加强写入过程：

| 原实现 | 完善后 |
| --- | --- |
| `insert into t_cart values()` | 明确指定字段，插入请求数据和服务端信息 |
| 没有重复加购逻辑 | 唯一索引配合 `ON DUPLICATE KEY UPDATE` 原子累加 |
| Mapper 返回 void | 返回受影响行数，Service 检查是否写入成功 |
| 创建、更新时间未填充 | 由服务端填写，重复加购保留创建时间 |
| 普通查询后直接写购物车 | 同一事务内按门店、菜品顺序锁定，再检查当前状态 |
| `cart.setDishId(cart.getDishId())` | 删除无效自赋值，只复制业务需要的输入字段 |

## 二、Controller：接收 JSON，调用业务层

你的写法已正确，继续保留：

```java
@PostMapping
public Result add(@Validated(Cart.Add.class) @RequestBody Cart cart) {
    cartService.add(cart);
    return Result.success();
}
```

类上的 `/app/cart` 就是完整地址。新增参数校验确保菜品 ID、数量不能为空，并且大于等于 1。

Service 同样检查参数，使内部直接调用时也不会绕过必要的业务校验。

## 三、Service：身份和门店由服务端确定

```java
Long userId = UserContextUtil.getCurrentUserId();
Dish dish = dishMapper.findById(cart.getDishId());
```

第一行回答“谁在加购”，第二行找到“正在加购的是哪道菜”。菜品记录中保存了 `storeId`，不需要相信前端传入的门店。

为了与管理端下架、删除等操作协调，流程是：

```text
按 dishId 普通查询，取得所属门店
→ 锁定这家门店
→ 按菜品 ID、门店 ID 锁定并重新查询菜品
→ 再检查菜品是否存在、是否上架
→ 写入购物车
→ 提交事务，释放数据库行锁
```

为什么要重新查询？因为第一次查到菜品后，其他请求可能正在下架或删除它。等待门店锁后，要以锁定查询得到的状态为准。

`@Transactional` 让检查和写入处于同一事务；实际的行锁由 Mapper 中已有的 `FOR UPDATE` 查询取得。各处沿用“先门店、再菜品”的顺序，避免相反锁顺序造成相互等待。

下架菜品使用文档要求的提示：

```json
{"code":1,"message":"该菜品已下架","data":null}
```

## 四、准备真正写入的 Cart 对象

```java
Cart newCart = new Cart();
newCart.setUserId(userId);
newCart.setStoreId(storeId);
newCart.setDishId(dish.getId());
newCart.setQuantity(cart.getQuantity());
LocalDateTime now = LocalDateTime.now();
newCart.setCreateTime(now);
newCart.setUpdateTime(now);
```

请求中的菜品 ID 用来查菜品，数量用来表示本次加几份。用户、门店和时间都由服务端填写。客户端额外填写的购物车主键、用户和门店信息不会决定写入目标。

主键不放进 INSERT 字段，由数据库自增生成。9.2 不返回新增 ID，因此没有添加回填主键的 `@Options`。

## 五、Mapper：一条 SQL 处理新增和累加

```java
@Insert("insert into t_cart(user_id, store_id, dish_id, quantity, create_time, update_time) " +
        "values(#{userId}, #{storeId}, #{dishId}, #{quantity}, #{createTime}, #{updateTime}) " +
        "on duplicate key update quantity = quantity + values(quantity), " +
        "update_time = values(update_time)")
int add(Cart cart);
```

### 1. 第一次加购

假设用户 8 添加菜品 101，本次新增数量 2：

```text
购物车中没有“用户8 + 菜品101”
→ INSERT 新增一行
→ quantity = 2
```

### 2. 再次加购

表上已有唯一索引：

```sql
unique key uk_user_dish(user_id, dish_id)
```

同一用户再次添加同一道菜，会与这条唯一索引冲突，于是进入 `ON DUPLICATE KEY UPDATE`。

```sql
quantity = quantity + values(quantity)
```

左侧及右侧原有的 `quantity` 表示已有记录的数量；`values(quantity)` 表示本次尝试插入的新增数量。

例如：

```text
已有数量 2，本次再加 3
→ 2 + 3 = 5
→ 保留一行，数量变成 5
```

另一个用户添加菜品 101 时，`user_id` 不同，不会修改用户 8 的记录。

### 3. 时间字段

重复时只更新数量和 `update_time`，所以原主键及 `create_time` 保留。

### 4. 并发与幂等的区别

“读取旧数量，再由 Java 加好后覆盖回去”可能让并发请求覆盖彼此的结果。这里由数据库在同一条 upsert 中处理累加，避免这种丢失更新，也依赖唯一索引防止重复行。

接口文档中的“天然幂等”表述不准确：同一个加购请求发送两次，会累加两次。原子累加不是请求去重。如果以后需要识别重试请求，需要额外的请求标识与去重设计，本次未引入该机制。

## 六、检查写入结果，失败时回滚

MySQL 中，正常插入通常影响 1 行，重复键后更新通常影响 2 行。Service 接受这两种结果，其他结果抛出业务异常。

```java
if (rows != 1 && rows != 2) {
    throw new BizException("加入购物车失败，请重试");
}
```

数量累加超出数据库 INT 范围等字段约束问题，会转换为“加入购物车失败，请检查数量”。异常保留原始原因，事务回滚，已有数量和更新时间不会留下部分修改。

## 七、跨门店购物车与验证范围

文档建议前端在切换门店时提示清空购物车，本次加购没有擅自删除其他门店的条目。9.1 已支持按门店或查看自己的全部条目；清空应当是独立、明确的业务操作。

测试在独立 H2 的 MySQL 模式执行真实 upsert，Redis 使用模拟对象。覆盖首次新增、重复累加、不同用户、字段伪造、跨店保留、参数错误、数量溢出、事务回滚、并发累加和等待管理端事务后重新检查菜品状态。

这是 H2 与模拟 Redis 的验证，不等同于真实 MySQL、Redis 环境联调。
