# 8.3 用户端菜品列表与缓存实现讲解

## 1. 从“查菜单”理解缓存

可以把数据库看作厨房里最新的菜单记录，把 Redis 看作前台留存的菜单副本。

- 副本还在：直接交给顾客，不必每次去厨房查询。
- 副本没有了：安排一个人重新查询，其他请求稍等，避免大家同时去问。
- 厨房修改了菜单：数据库提交成功后，撤掉旧副本，下次重新获取。

文档要求的不只是查询 SQL，还包括 Redis 缓存、互斥回源、空结果缓存和随机过期时间。

## 2. 你这次已经写对了什么

相比 8.2 时把分类查询写到门店模块、返回 `Store`，这次你已经做到了：

1. 在 `AppDishController`、`AppDishService` 中编写菜品查询。
2. 返回菜品列表，逐层把数据返回给 Controller。
3. 接收必传 `storeId` 和可选 `categoryId`。
4. 调用已有 `DishMapper.list`，传入上架状态 `1`，并传入门店 ID。
5. 知道不传分类时应查询本店全部上架菜品。

这些都是实质进步。本次原代码主要缺少 `@GetMapping("/list")`、非正数 ID 检查，以及文档规定的缓存策略。请求映射是 8.2 和这次都遗漏的地方，写完 Controller 后可以先确认“请求路径、请求方式、参数来源、返回类型”。

你写的两条查询分支也可以合并，因为已有 SQL 在 `categoryId == null` 时就不会限制分类：

```java
dishMapper.list(null, 1, categoryId, storeId);
```

本次保留并复用了这个 Mapper，没有重写管理端 SQL。

## 3. Controller → Service → Mapper → 数据库

### Controller：接收请求

文件：`controller/app/AppDishController.java`。

```java
@GetMapping("/list")
public Result<List<AppDishVO>> find(
        @RequestParam("storeId") Long storeId,
        @RequestParam(value = "categoryId", required = false) Long categoryId) {
    List<AppDishVO> dishes = appDishService.find(storeId, categoryId);
    return Result.success(dishes);
}
```

请求示例：

```http
GET /app/dish/list?storeId=1&categoryId=11
Authorization: 用户登录返回的完整 token
```

不传 `categoryId` 时查询本店全部上架菜品。两个 ID 都来自 URL，顾客身份仍由已有登录拦截器验证。顾客可以切换门店，不使用员工绑定门店的权限工具。

### Service：校验参数，再通过缓存查询

文件：`service/impl/AppDishServiceimpl.java`。

`storeId` 必须非空且大于 0；`categoryId` 可以不传，但传入时必须大于 0。缺少参数和参数类型错误继续交给已有全局异常处理器。

核心调用是：

```java
return dishCacheUtil.getOrLoad(storeId, categoryId,
        () -> dishMapper.list(null, 1, categoryId, storeId).stream()
                .map(AppDishVO::from).toList());
```

这里的 `() -> ...` 可以理解为“先把查数据库这件事交给缓存工具，需要时再执行”。缓存命中时不会执行里面的 SQL。`Supplier` 就是这样一个可以在需要时取得结果的任务。

`AppDishVO::from` 等价于 `dish -> AppDishVO.from(dish)`，把数据库实体转成返回对象。它只包含文档要求的九个字段，价格仍用 `BigDecimal`，创建时间和更新时间不返回给用户端。

### Mapper：复用你已有的条件查询

实际使用的是 `DishMapper.list(null, 1, categoryId, storeId)`。其含义是：

```sql
select * from t_dish
where store_id = #{storeId}
  and status = 1
  and (#{categoryId} is null or category_id = #{categoryId})
order by sort asc, id asc;
```

门店条件防止混入其他门店；状态条件排除下架菜品；分类不传时不限制分类。同排序号再按 ID 排序，保证结果顺序稳定。

没有匹配数据时返回空数组，包括不存在的分类或门店。遵循文档，只按菜品上架状态筛选，没有额外加入分类启用、门店营业时间等筛选规则。

## 4. Redis 缓存如何工作

代码集中在 `utils/DishCacheUtil.java`，Service 保留业务参数和查询，缓存工具负责缓存及并发处理。

### 缓存 key：门店必须在里面

| 查询 | key |
| --- | --- |
| 门店 1、分类 11 | `dish:1:11` |
| 门店 2、分类 11 | `dish:2:11` |
| 门店 1、全部分类 | `dish:1:all` |

不同门店使用不同 key，全部分类和某个分类也不共用一个 key。

Redis 保存的是菜品列表 JSON。命中后把 JSON 转回 `List<AppDishVO>`，所以命中与查库时返回结构相同。格式损坏、包含错误门店或下架状态的缓存会视为未命中，重新查询。

### 未命中时的执行顺序

```text
查缓存
→ 命中：直接返回，包括 []
→ 未命中：尝试取得当前 key 对应的 Redis 锁
    → 取得锁：再次检查缓存
        → 仍未命中：查库、写缓存、释放锁、返回
    → 未取得锁：短暂等待，重新检查缓存和尝试取锁
```

拿到锁后再次检查，是因为前一个请求可能刚刚重建完缓存。再次检查可以避免重复查询数据库。

锁采用 `setIfAbsent`，有 15 秒过期时间。每次锁都有随机持有者标识。解锁使用 Lua 比较持有者再删除，两个操作由 Redis 原子执行，避免误删锁过期后被其他请求取得的新锁。

等待采用有限次数重试，约 2 秒仍然无法取得结果时提示“菜品正在加载，请稍后重试”。数据库或网络操作本身的耗时不包含在这约 2 秒的等待时间内。不会无限递归，也不会让所有抢锁失败的请求同时查库。

### 两种过期时间

| 结果 | 缓存时长 | 作用 |
| --- | --- | --- |
| 空列表 `[]` | 60 秒 | 同样的无结果请求不必每次查库，缓解缓存穿透 |
| 非空列表 | 1800 秒 + 随机 1～300 秒 | 避免大量 key 在同一时刻集中失效，缓解缓存雪崩 |

这里判断缓存是否存在用的是“是否为 null”，而不是“列表是否为空”。否则空结果虽然写入 Redis，下次仍会被当作未命中。

## 5. 写库之后，旧缓存如何失效

原来的 `clearDishCacheAfterCommit` 继续作为管理端调用入口，内部委托给公共缓存工具。修改、上下架、删除已有的提交后清理逻辑得到保留，同时补充了两处：

- 新增菜品后清缓存：否则之前缓存的空分类或全部菜品列表可能看不到新菜。
- 整店删除后清缓存：否则用户还可能读到已删除门店的旧菜单。

数据库事务提交成功后，才按 `dish:{storeId}:*` 扫描并分批清理缓存。事务回滚时不清理，其他门店缓存不受影响。锁 key 以 `lock:dish:` 开头，不在这个清理范围内。

### 为什么还记录一个版本号

还需要考虑这种交错：

```text
请求 A 查到旧菜单，还没写缓存
→ 请求 B 修改数据库并清掉旧缓存
→ 请求 A 把刚查到的旧菜单又写回缓存
```

为此，每家门店有 `dish:version:{storeId}` 元数据。查询前读取版本，写库提交后的缓存清理先增加版本。缓存回写使用 Lua 同时检查：锁仍属于本请求，门店版本也没有变化。条件不满足，就不缓存这次结果。

版本 key 不属于菜品列表 key 的扫描范围。它用于防止正常运行时旧查询结果重新填回缓存；它不代表 MySQL 与 Redis 之间已经具备强一致事务。提交后 Redis 清理失败会记录日志，缓存仍受 TTL 限制。

## 6. 异常处理和验证范围

缓存读取、取锁或写入出现 Redis 异常时，尽量通过数据库完成本次业务查询；数据库查询失败则直接向上传播，不把它误当成 Redis 失败而反复查库。解锁失败依靠锁过期兜底。已有登录验证仍然依赖 Redis，因此整套 Redis 不可用时，请求也可能先被登录拦截器拒绝。

测试使用独立 H2 执行真实查询，带状态的 Redis 模拟对象验证缓存、锁持有者与版本变化的契约；并发测试覆盖同一 key 的回源合并。同时验证新增、修改、上下架、删除、整店删除和事务回滚对读取缓存的影响。

这些测试没有连接业务数据库，也没有在真实 Redis 上执行 Lua，不能替代真实 MySQL、Redis 环境联调。
