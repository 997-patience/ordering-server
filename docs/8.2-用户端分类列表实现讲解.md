# 8.2 用户端分类列表实现讲解

## 1. 这个接口到底查询什么

顾客在首页选择一家门店，然后查看这家门店下启用的菜品分类。

```http
GET /app/category/list?storeId=1
Authorization: 7.2 登录返回的用户 token
```

`storeId` 来自 URL 查询参数；登录身份来自 token。两者用途不同：前者表示“我正在看哪家店”，后者表示“我是谁”。顾客可以切换门店，不需要管理员角色，也不需要绑定门店。

成功响应的数据是一个分类数组：

```json
{
  "code": 0,
  "message": "操作成功",
  "data": [
    {"id": 3, "name": "热菜", "sort": 1},
    {"id": 1, "name": "主食", "sort": 2}
  ]
}
```

这里是分类列表，返回类型应为 `List<AppCategoryVO>`。`Store` 表示一家门店，`Dish` 表示一道菜，都不是本接口的返回对象。

## 2. 与你上一次的代码比较

8.1 初写时，你的查询方法返回 `void`，没有把查询结果逐层交回前端。这次你已经主动接收 `storeId`，调用 Service，并用 `Result.success(...)` 返回结果，还加入了空值检查。这说明你已经开始关注完整的调用链。

本次主要需要纠正的是“查什么、放在哪、返回什么”：

| 你原来的实现 | 本次调整 | 原因 |
| --- | --- | --- |
| 在 `AppStoreController` 写 `findDishes` | 改到 `AppCategoryController.list` | 8.2 属于分类列表，路径是 `/app/category/list` |
| 方法只有 `@RequestParam` | 增加 `@GetMapping("/list")` | 参数注解只负责接收参数，映射注解才负责接入 HTTP 请求 |
| 返回单个 `Store` | 返回 `List<AppCategoryVO>` | 文档的 data 是分类数组 |
| 调用 `StoreMapper.findByIdForUpdate` | 调用 `CategoryMapper.listEnabledByStoreId` | 原 SQL 查询门店表，无法得到分类；普通浏览也不需要锁定门店 |
| 只检查 `storeId == null` | 同时拒绝小于 1 的 ID | 0 和负数也不是有效门店 ID |

原来放错位置、尚未映射成接口的 `findDishes` 方法已从门店 Controller、Service、实现类中移除。8.1 的营业门店列表继续保留。

## 3. Controller：接收参数并返回结果

文件：`src/main/java/com/wys/orderingserver/controller/app/AppCategoryController.java`。

```java
@GetMapping("/list")
public Result<List<AppCategoryVO>> list(@RequestParam("storeId") Long storeId) {
    return Result.success(appCategoryService.list(storeId));
}
```

类上的 `@RequestMapping("/app/category")` 与方法上的 `/list` 组成完整路径。

`@RequestParam("storeId")` 从 `?storeId=1` 取出值，转换为 `Long`。默认要求参数存在；缺少参数、传入无法转换的内容时，由已有全局异常处理器返回参数错误。

方法中的一行可以拆成两行理解：

```java
List<AppCategoryVO> categories = appCategoryService.list(storeId);
return Result.success(categories);
```

## 4. Service：校验有效 ID，再查询

接口 `AppCategoryService` 声明：

```java
List<AppCategoryVO> list(Long storeId);
```

实现类 `AppCategoryServiceimpl`：

```java
@Override
public List<AppCategoryVO> list(Long storeId) {
    if (storeId == null || storeId < 1) {
        throw new BizException("请选择有效的门店ID");
    }
    return categoryMapper.listEnabledByStoreId(storeId);
}
```

Service 负责检查业务参数，再把 Mapper 查询结果返回给 Controller。这里不调用 `AdminContextUtil`：登录及用户身份检查已经由拦截器负责，顾客选店也不遵循员工绑定门店的规则。

## 5. Mapper：SQL 必须同时限制门店和启用状态

文件：`src/main/java/com/wys/orderingserver/mapper/CategoryMapper.java`。

```java
@Select("select id, name, sort from t_category " +
        "where store_id = #{storeId} and status = 1 " +
        "order by sort asc, id asc")
List<AppCategoryVO> listEnabledByStoreId(@Param("storeId") Long storeId);
```

- `store_id = #{storeId}`：只查顾客选中门店的分类，不混入其他门店的数据。
- `status = 1`：只返回启用分类。
- `order by sort asc, id asc`：排序号越小越靠前；排序号相同时按主键排序，保证顺序稳定。
- `select id, name, sort`：只读取本接口需要的三个字段。

管理端原来的 `getCategory` 查询包含禁用分类，所以没有修改它，而是增加用户端所需的查询方法。两端共享 Mapper，但可以根据业务需要使用不同 SQL。

本接口没有分页，也不需要 `FOR UPDATE`；没有查询到分类时返回成功与空数组。文档没有规定“门店不存在”的专用失败响应，本次将不存在门店、无分类、全部分类禁用都按无匹配结果返回 `[]`。没有额外加入营业时间或门店状态限制，查询条件遵循 8.2 文档。

## 6. 为什么增加 AppCategoryVO

文件：`src/main/java/com/wys/orderingserver/pojo/AppCategoryVO.java`。

这个类只包含 `id`、`name`、`sort`，专门表示返回给前端的一条分类信息。MyBatis 直接把所选的三列映射到这个对象。

原来的 `Category` 还包含 `storeId`、`status` 和时间字段。使用独立返回对象可以精确控制用户端 JSON，而不需要修改管理端使用的实体类。
