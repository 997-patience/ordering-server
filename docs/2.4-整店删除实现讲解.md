# 2.4 整店删除实现讲解

本次按你的新需求实现：删除门店时，一并删除本店分类、菜品、订单、订单明细、购物车记录和员工账号。包括历史订单；这是永久删除数据库记录，不是打烊或解除关联。

接口仍是 `DELETE /admin/store?id=门店编号`，仅超级管理员可以调用。

## 1. 删除哪些数据

| 表 | 如何定位本店数据 |
| --- | --- |
| t_order_detail | order_id 属于本店的订单 |
| t_orders | store_id 等于目标门店 ID |
| t_cart | store_id 等于目标门店 ID |
| t_dish | store_id 等于目标门店 ID |
| t_category | store_id 等于目标门店 ID |
| t_employee | store_id 等于目标门店 ID |
| t_store | id 等于目标门店 ID |

其他门店的数据保留。顾客账号 t_user 和顾客地址 t_address 是平台共享数据，不随某一家门店删除。没有绑定该店的超级管理员账号同样保留。

这里清理的是数据库记录；菜品图片字段会随菜品记录删除，但上传到磁盘的图片文件没有自动删除。文件可能被其他数据引用，文件清理需要另外设计。

## 2. Controller 仍只负责接收门店 ID

```java
@DeleteMapping
public Result delete(@RequestParam("id") Long id) {
    storeService.delete(id);
    return Result.success();
}
```

之前放在 Long 参数上的 `@Validated(Store.Add.class)` 不适用于门店新增实体校验。本次删除该注解，ID 是否大于 0 由 Service 检查。

## 3. Mapper 为每张表提供删除 SQL

写法继续沿用 EmployeeMapper 的 SQL 注解风格。以分类为例：

```java
@Delete("delete from t_category where store_id = #{storeId}")
int deleteCategoriesByStoreId(Long storeId);
```

条件使用 store_id，表示删除这家门店的全部分类，不是只删除分类主键等于门店 ID 的一条记录。

订单明细没有 store_id，需要通过订单主表定位：

```java
@Delete("delete from t_order_detail where order_id in " +
        "(select id from t_orders where store_id = #{storeId})")
int deleteOrderDetailsByStoreId(Long storeId);
```

内层查询先找出本店订单 ID，外层删除这些订单的明细。必须先删明细再删订单，否则后续就无法通过订单主表找到应删除的明细。

最后删除门店的方法返回 int：

```java
@Delete("delete from t_store where id = #{id}")
int delete(Long id);
```

返回值代表实际删除条数。目标门店应当删除 1 条，否则 Service 抛出异常。

## 4. Service 在同一个事务中协调全部操作

关键流程：

```java
@Override
@Transactional
public void delete(Long id) {
    // 完整代码先检查 ID、登录信息和 role=1，再锁定并检查门店。

    storeMapper.deleteOrderDetailsByStoreId(id);
    storeMapper.deleteOrdersByStoreId(id);
    storeMapper.deleteCartsByStoreId(id);
    storeMapper.deleteDishesByStoreId(id);
    storeMapper.deleteCategoriesByStoreId(id);
    storeMapper.deleteEmployeesByStoreId(id);

    if (storeMapper.delete(id) != 1) {
        throw new BizException("门店删除失败，请刷新后重试");
    }
}
```

这是流程节选，权限和存在性检查见实际 StoreServiceimpl.delete。

`@Transactional` 将这些 SQL 放在同一个数据库事务中。正常返回后统一提交；发生数据库异常或 BizException 时回滚。BizException 继承 RuntimeException，符合 Spring 默认回滚规则。

例如已经删除明细、订单和购物车，删除菜品时发生异常，前面已经删除的记录也会恢复，不会只清理一半。

## 5. 为什么查询门店时加 FOR UPDATE

```java
@Select("select * from t_store where id = #{id} for update")
Store findByIdForUpdate(Long id);
```

这是在事务中对目标门店加行锁，锁一直持有到提交或回滚。两个删除请求同时操作同一家门店时，后来的请求需要等待；第一个完成后，第二个查询不到门店，返回“门店不存在”。

但门店行锁本身不会自动阻止所有关联表写入，必须配合下面的外键约束。仅使用 @Transactional 也不能代替外键。

## 6. 数据库需要应用外键脚本

脚本位置：`src/main/resources/db/store-delete-foreign-keys.sql`。

它为员工、分类、菜品、购物车、订单的 store_id 添加指向门店的外键，并为订单明细的 order_id 添加指向订单的外键。采用 ON DELETE RESTRICT，由 Service 明确按顺序删除关联数据。

效果：

- 已删除门店不能再被新分类、菜品、订单等记录引用。
- 已删除订单不能再被新订单明细引用。
- 如果删除过程中出现其他关联写入，数据库会等待、拒绝写入或阻止删除，避免留下孤立记录。

该脚本不会被应用自动运行，本次也没有对现有 MySQL 数据库执行它。要让现有数据库具备上述并发约束，需要在正确的 ordering 数据库应用一次。旧数据如果已经存在失效引用，应先修复，否则添加外键会失败。

脚本不包含 DROP DATABASE 或业务数据 DELETE。不要为了添加外键而重新运行整个 ordering-ddl.sql；原始建表脚本会重建数据库。

## 7. 为什么还修改了登录拦截器

原来只要 Redis 中还有 token、JWT 校验通过，就认为登录有效。删除员工数据库记录不会自动删除 Redis 令牌。

现在，对于包含 role 的员工令牌，LoginInterceptor 还会根据员工 ID 查询 t_employee：

```text
员工存在且启用 → 继续处理请求
员工不存在或被禁用 → HTTP 401
```

因此，删店后即使员工旧 token 还在 Redis 中，它也无法通过后续请求的校验。Redis 中的令牌键保留至原有过期时间；本次没有扫描或批量删除其他登录会话。

这是对后续请求的检查，已经进入业务处理的请求不会被这次检查自动中断。关联写入最终由数据库约束兜底。

## 8. 如何验证

新增 StoreDeleteIntegrationTests，使用独立 H2 内存数据库，初始化时加载与交付相同的外键脚本。Redis 存取使用测试替身，SQL、Service 事务和登录拦截器执行真实代码。

覆盖：

1. 本店全部关联记录删除，其他门店和共享顾客数据保留。
2. 无商品的门店也能正常删除，并清理绑定员工。
3. 门店管理员、顾客、未登录请求不能删除。
4. 非法 ID、不存在的门店不会删除任何数据。
5. 最后一步失败或中途 SQL 异常时，前面的删除全部回滚。
6. 被删除员工的旧 token 返回 401，其他门店员工仍能访问。
7. 外键拒绝给已删除门店新增分类。
8. 两个并发删除请求只允许一个成功。

在项目目录运行全部测试：

```powershell
./mvnw.cmd test
```
