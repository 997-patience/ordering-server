# 4.3 修改菜品实现讲解

接口为 `PUT /admin/dish`，请求体使用 JSON。图片上传仍留到 11.1，修改时省略 `image` 会保留原图片地址。

## 1. 请求从哪里来

```http
PUT /admin/dish
Authorization: 登录获得的原始token
Content-Type: application/json
```

```json
{
  "id": 1,
  "name": "宫保鸡丁大份",
  "categoryId": 1,
  "price": 42.00
}
```

这里的菜品 ID 和分类 ID 都要替换为当前门店真实的数据。`id` 指定修改哪道菜，`categoryId` 指定这道菜修改后的分类，二者用途不同。

Controller 使用 `@Validated(Dish.Update.class) @RequestBody Dish dish`：JSON 转成对象后，启用更新校验组，要求提供主键、名称、分类和价格，再调用 Service。

## 2. 为什么修改不能直接照搬新增

| 字段或行为 | 4.2 新增 | 4.3 修改 |
| --- | --- | --- |
| id | 清空客户端值，由数据库生成 | 必须保留，用来定位目标菜品 |
| storeId | 从登录信息获取后填充 | 从登录信息获取，用来限定修改范围；不会移动菜品门店 |
| categoryId | 分类必须属于当前门店 | 修改后的分类也必须属于当前门店 |
| status、sort | 不传时默认 1、0 | 不传时保留原值 |
| image、description | 可为空 | 不传或传 null 时保留，传空字符串时清空字符串内容 |
| createTime | 后端生成 | 保留原创建时间 |
| updateTime | 后端生成 | 后端重新生成 |

你原来在修改方法中调用了 `dish.setId(null)`。这适用于新增，修改时会丢掉目标 ID，因此已经去掉。

## 3. Service 的运行顺序

`DishServiceimpl.updateDish()` 在一个事务中依次执行：

1. 通过 `AdminContextUtil.getCurrentAdminStoreId()` 检查登录、管理员身份和门店绑定。
2. 校验菜品 ID，并调用新增、修改共用的 `validateDishFields()`，检查名称、分类、价格、状态和字段长度，整理名称与金额。
3. 先锁定并检查门店，再按“分类 ID + 当前门店 ID”查询并锁定分类，与新增、分类删除和整店删除遵循相同顺序。
4. 用登录信息覆盖请求对象的门店 ID，生成新的更新时间，保留目标菜品 ID。
5. 调用 Mapper 更新；匹配行数不是 1 时，提示“菜品不存在或不属于当前门店”并回滚。
6. 注册事务提交后的缓存清理操作。事务回滚时不会执行该操作。

“门店存在”和“这道菜属于门店”是两项不同的检查。查询门店只能证明门店存在，真正限制菜品操作范围的是 UPDATE 中的 `id + store_id` 条件。

## 4. Mapper 为什么必须写 WHERE

你原来的 UPDATE 只有 SET 部分，没有 WHERE 条件。如果直接执行，会尝试修改整张菜品表。

现在的 SQL 是：

```java
@Update("update t_dish set name = #{name}, category_id = #{categoryId}, price = #{price}, " +
        "image = coalesce(#{image}, image), description = coalesce(#{description}, description), " +
        "status = coalesce(#{status}, status), sort = coalesce(#{sort}, sort), " +
        "update_time = #{updateTime} " +
        "where id = #{id} and store_id = #{storeId}")
int updateDish(Dish dish);
```

`where id = #{id}` 定位目标菜品，`and store_id = #{storeId}` 限定当前门店，两个条件必须同时满足。

`coalesce(#{status}, status)` 会选择第一个非 null 的值：前端传 0 就更新为 0，传 1 就更新为 1，不传则使用数据库原来的 status。这里判断的是 null，不会把数值 0 当成没传。

图片、描述和排序采用同样的保留规则。当前实体不能区分“字段未出现”和“显式传 null”，这两种情况都按保留处理；图片或描述传 `""` 则保存为空字符串。

## 5. 缓存为什么在事务提交后清理

文档规定先更新数据库，再删除菜品列表缓存。如果数据库还没提交就清缓存，其他请求可能先读到旧数据并写回缓存。

当前通过 `TransactionSynchronization.afterCommit()` 在数据库提交后清理 `dish:{storeId}:*`，使用 Redis SCAN 遍历并分批删除，每批最多 200 个 key。

例如修改门店 1 的菜品时，清理 `dish:1:11`、`dish:1:12`、`dish:1:all` 等列表缓存，覆盖旧分类、新分类和全部上架菜品列表；门店 2、门店 10 的缓存及登录令牌不在范围内。

本阶段完成更新后的缓存失效。用户端读取缓存、未命中查库和重新写入的流程，按开发顺序留到 8.3。Redis 清理异常会记录错误日志，数据库已经提交，因此接口仍返回数据库修改成功；当前没有持久化的缓存清理重试任务。

## 6. 与上一次 4.2 的对比

这次你已经主动使用更新校验组，检查分类 ID 和价格，并尝试复用门店加锁查询，说明你正在把新增接口的处理步骤迁移到修改接口。需要继续练习的是识别业务差异：新增生成主键、补默认值，修改保留主键和未传字段，并用 SQL 精确限定目标记录。校验方法也已经提取，新增和修改可以共享同一套基础规则。

测试在独立 H2 数据库执行真实 SQL，并模拟 Redis，验证只修改目标菜品、跨店限制、可选字段保留、事务回滚、提交后清缓存及分批清理。真实 MySQL、Redis 联调尚未覆盖。
