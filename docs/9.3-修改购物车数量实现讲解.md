# 9.3 修改购物车数量实现讲解

接口是 `PUT /app/cart`，请求体是 JSON：

```json
{"dishId":101,"quantity":5}
```

意思是把“当前登录用户购物车中的菜品 101”设置为 5 份。原来是 2 份，修改后就是 5 份；没有这个条目则返回失败，不会新增。

## 一、这次已经写对了什么

你已经使用 `@PutMapping` 表达修改操作，也调用 `UserContextUtil` 取得当前用户，在 SQL 中同时限定了 `dish_id` 和 `user_id`，还检查了更新行数。

相比 9.1 初写时遗漏用户条件，这次你已经主动保护了购物车归属。这是实际的进步。

主要问题与修正如下：

| 原实现 | 修正 |
| --- | --- |
| Controller 没有 `@RequestBody` | 明确接收文档规定的 JSON |
| `Cart.Update` 要求购物车主键 id 必填 | 取消该要求，9.3 只需要 dishId、quantity |
| 数量非法提示“购物车为空” | 改为准确的参数提示 |
| 没有更新 update_time | 数量变化时填写服务端当前时间 |
| 更新不到就统一“更新失败” | 先按当前用户、菜品查到已有条目，否则提示“购物车中没有该菜品” |
| 相同数量也依赖 UPDATE 返回行数 | 相同目标值直接成功，避免驱动对未变化数据计数不同导致误判 |

## 二、先区别 9.2 和 9.3

| 操作 | quantity 的含义 | 原来 2 份，传入 3 后 |
| --- | --- | --- |
| 9.2 POST 加入购物车 | 本次新增几份 | 变成 5 份 |
| 9.3 PUT 修改数量 | 最终要有几份 | 变成 3 份 |

因此 9.3 使用 `set quantity = #{quantity}`，而不是 `quantity + #{quantity}`。

## 三、Controller：让 JSON 进入 Cart 对象

```java
@PutMapping
public Result update(@Validated(Cart.Update.class) @RequestBody Cart cart) {
    cartService.update(cart);
    return Result.success();
}
```

`@RequestBody` 把 JSON 中的 dishId、quantity 赋给 Cart。新增分组校验仍保留，更新分组也继承 Default，从而检查菜品 ID、数量不能为空且至少为 1。

Cart 主键 id 由数据库生成；本接口按照 `user_id + dish_id` 定位，不要求前端知道购物车项的主键。因此移除了 Cart.id 的 Update 分组必填约束。

0 或负数量会失败，不会被当成删除操作。缺少或错误 JSON 继续由现有全局异常处理器转换为统一错误响应。

## 四、Service：检查当前用户，锁定已有条目

```java
@Transactional
public void update(Cart cart) {
    Long userId = UserContextUtil.getCurrentUserId();
    if (cart == null || cart.getDishId() == null || cart.getDishId() < 1) {
        throw new BizException("请选择有效的菜品ID");
    }
    if (cart.getQuantity() == null || cart.getQuantity() < 1) {
        throw new BizException("数量至少为1");
    }
    Cart existing = cartMapper.findByUserIdAndDishIdForUpdate(userId, cart.getDishId());
    if (existing == null) {
        throw new BizException("购物车中没有该菜品");
    }
    if (cart.getQuantity().equals(existing.getQuantity())) {
        return;
    }
    int rows = cartMapper.update(cart.getDishId(), cart.getQuantity(), userId, LocalDateTime.now());
    if (rows != 1) {
        throw new BizException("购物车数量修改失败，请重试");
    }
}
```

这里的 userId 来自登录信息，前端传入 userId、storeId 或购物车主键，都不会改变操作目标。

`existing` 是当前用户在数据库里的购物车记录，用于确认条目存在、取得原数量；不会拿前端输入的身份字段覆盖它。

9.3 文档只要求修改本人已有条目的数量，没有新增“必须上架”的条件。因此本次不再套用加购的菜品状态检查：已有下架条目仍可调整数量。9.2 的新增、累加操作继续拒绝下架菜品，原逻辑保留。

## 五、Mapper：读取和更新都限定当前用户

读取已有条目：

```java
@Select("select * from t_cart where user_id = #{userId} and dish_id = #{dishId} for update")
Cart findByUserIdAndDishIdForUpdate(@Param("userId") Long userId, @Param("dishId") Long dishId);
```

这条 SQL 只定位当前用户和指定菜品。没有自己的记录时，即使其他用户购买了同一道菜，也返回 null。

`FOR UPDATE` 在事务里锁定这条购物车记录，让并发修改、加购或删除等待当前事务结束。

更新：

```java
@Update("update t_cart set quantity = #{quantity}, update_time = #{updateTime} " +
        "where dish_id = #{dishId} and user_id = #{userId}")
int update(@Param("dishId") Long dishId, @Param("quantity") Integer quantity,
           @Param("userId") Long userId, @Param("updateTime") LocalDateTime updateTime);
```

这里仍保留完整的用户、菜品条件。即使业务层已经读取并检查过，写 SQL 本身也不能省略用户条件。

仅修改数量和更新时间，原主键、用户、门店、菜品 ID 和创建时间都保留。

## 六、为什么数量相同时直接成功

假设原来就是 5，前端重复提交“改成 5”。业务目标已经达到，应当成功。

数据库驱动对没有实际变化的 UPDATE 可能采用不同的行数统计，时间字段在同一秒也可能没有变化。我们先在锁定状态下比较原数量，已经相同就不执行 UPDATE，因此不依赖这种计数差异。

如果原来为 2，第一次设为 5 后再次提交 5，数量仍为 5，也不会再次改变更新时间。这与 9.2 每次加购都累加不同。

## 七、事务与并发顺序

读取加锁、检查和更新位于同一事务。更新失败抛出业务异常后，数量和时间一并回滚。

与加购同时发生时，顺序决定合理结果。例如初始数量 2：

```text
先设为5，再加2 → 7
先加2，再设为5 → 5
```

9.3 只需要锁定被修改的购物车行，不会在拿到购物车锁后再去锁门店或菜品。9.2 取得门店、菜品锁后，写购物车时也要等待这条购物车记录的锁，因此可以协调操作顺序。

如果删除先提交，更新请求等待后会发现条目已经不存在，返回错误，不会重新创建记录。

## 八、完整执行与验证范围

```text
PUT /app/cart，JSON 传 dishId、quantity
→ 拦截器验证顾客身份
→ Controller 解析 JSON、校验字段
→ Service 读取当前用户 ID
→ Mapper 按 user_id + dish_id 锁定已有购物车行
→ 数量相同直接成功；不同则设置目标值及更新时间
→ 检查更新行数、提交事务
→ 返回 Result.success()
```

该验证不等同于真实 MySQL、Redis 环境联调。
