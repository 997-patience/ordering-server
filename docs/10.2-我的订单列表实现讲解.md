# 10.2 我的订单列表：检查结果与实现讲解

本次接口是 `GET /app/order/list`，分页查询当前登录顾客在所有门店的订单，按下单时间倒序展示。

## 一、你已经写对了什么

你已经主动完成了 Controller、Service 接口、实现类三层调用，并且正确使用了：

- `@GetMapping("/list")`。
- `@RequestParam` 接收 pageNum、pageSize 和可选 status。
- 页码、每页条数及订单状态的检查。
- `PageHelper.startPage()` 开启分页。
- try-with-resources 关闭 Page，避免分页上下文残留。
- `PageBean` 包装 total 和 items，并使用 Result.success 返回。

和 10.1 初稿相比，这次已经有了完整的分页业务骨架，可以正常编译。需要补强的地方，是根据接口的使用者调整数据范围和 SQL，而不是只把已有分页代码复制过来。

## 二、原来主要有哪些问题

原实现中：

```java
Long storeId = AdminContextUtil.getCurrentAdminStoreId();
orderMapper.list(storeId, status, null, null);
```

这是管理端的逻辑：识别门店管理员，查询这家店的订单。普通顾客没有管理员权限，因此正常用户会被权限检查拒绝；这个 Mapper 的条件也是门店范围，而非用户范围。

本接口应当改成：

```java
Long userId = UserContextUtil.getCurrentUserId();
orderMapper.listByUserId(userId, status);
```

| 场景 | 登录身份 | SQL 必须限定的范围 |
| --- | --- | --- |
| 管理端订单列表 | 门店管理员 | 本店订单：store_id |
| 用户端我的订单 | 登录顾客 | 本人订单：user_id |

此外，原来复用的 Mapper 按 id 升序，返回 Order 对象，既没有 storeName，也没有按照本接口要求的下单时间倒序排列。

## 三、现在每一层怎么执行

入口在 [AppOrderController 第 20 行](/D:/idea/Project/ordering-server/src/main/java/com/wys/orderingserver/controller/app/AppOrderController.java:20)：

```java
public Result<PageBean<AppOrderListVO>> page(
        @RequestParam("pageNum") Integer pageNum,
        @RequestParam("pageSize") Integer pageSize,
        @RequestParam(value = "status", required = false) Integer status)
```

请求例如：

```http
GET /app/order/list?pageNum=1&pageSize=5&status=1
Authorization: 登录接口返回的原始token
```

分页和状态来自 URL；userId 来自经过拦截器校验的登录信息。Controller 不接收要查询哪个用户的参数。

Controller、Service 接口、Service 实现的返回类型统一为 `PageBean<AppOrderListVO>`。列表项使用新的 [AppOrderListVO](/D:/idea/Project/ordering-server/src/main/java/com/wys/orderingserver/pojo/AppOrderListVO.java:11)，只包含文档中的 9 个字段：

```text
id、orderNo、storeId、storeName、amount、status、
pickupType、pickupTime、createTime
```

pickupTime 和 createTime 用 `@JsonFormat` 输出为 `yyyy-MM-dd HH:mm:ss`。金额保留 BigDecimal 类型。

业务入口在 [AppOrderServiceimpl 第 123 行](/D:/idea/Project/ordering-server/src/main/java/com/wys/orderingserver/service/impl/AppOrderServiceimpl.java:123)。它保留了你原有的参数检查，再取得当前顾客 userId，立即开启并执行目标分页查询：

```java
Long userId = UserContextUtil.getCurrentUserId();

try (Page<AppOrderListVO> page = PageHelper.startPage(pageNum, pageSize)) {
    orderMapper.listByUserId(userId, status);
    return new PageBean<>(page.getTotal(), page.getResult());
}
```

PageHelper 拦截随后执行的目标查询，自动执行总数 SQL 和当前页 SQL。`page.getTotal()` 是筛选后全部匹配记录数；`page.getResult()` 是当前页的记录。

例如本人有 6 笔订单，pageSize=2 时，total 仍然是 6，而不是当前页列表长度 2。

try 结束时会调用 Page.close() 清理分页上下文。查询抛异常时也会执行这项清理。你这次已经正确使用了这种写法。

## 四、Mapper SQL 为什么这样写

位置：[OrderMapper 第 20 行](/D:/idea/Project/ordering-server/src/main/java/com/wys/orderingserver/mapper/OrderMapper.java:20)。

```java
@Select("select o.id, o.order_no, o.store_id, s.name as store_name, o.amount, o.status, " +
        "o.pickup_type, o.pickup_time, o.create_time " +
        "from t_orders o left join t_store s on s.id = o.store_id " +
        "where o.user_id = #{userId} " +
        "and (#{status} is null or o.status = #{status}) " +
        "order by o.create_time desc, o.id desc")
List<AppOrderListVO> listByUserId(@Param("userId") Long userId,
                                @Param("status") Integer status);
```

`o` 是订单表别名，`s` 是门店表别名。

`s.id = o.store_id` 把订单关联到所属门店；`s.name as store_name` 取得门店名称。项目已开启下划线转驼峰，MyBatis 会把 store_name 填入 VO 的 storeName。

使用 LEFT JOIN，以订单为主；门店名称缺失时仍可保留匹配的订单。门店目前已打烊也不会把历史订单过滤掉。storeName 是本次查询时的门店名称，符合文档“关联查询”的口径。

`o.user_id = #{userId}` 是最关键的权限条件。它在 SQL 中直接过滤，所以统计总数和读取当前页都只针对本人。前端额外传 userId、storeId 或 role，不会改变此条件的来源。

状态为 null 时，不限制状态；否则只返回指定状态。

最后先按下单时间倒序，再按 ID 倒序。第二个排序条件保证同一秒创建的订单顺序稳定，减少翻页时因为顺序不确定而重复或遗漏的问题。它不能保证跨多个请求期间有新数据插入时分页位置完全不变；本接口仍按文档使用页码分页。

没有改变原来管理端的 list SQL；管理端继续按其本店权限和已有排序运行。

## 五、为什么给查询加只读事务

方法上的注解是：

```java
@Transactional(readOnly = true, isolation = Isolation.REPEATABLE_READ)
```

一次分页通常包含“查询总数”和“查询当前页”两条 SQL。如果两次查询之间有人新增或取消订单，结果可能使用两个不同时间点的数据。

在 MySQL InnoDB 的可重复读事务中，这两次普通查询可以读取同一快照，从而保持本次响应内部的总数、筛选条件和条目一致。这里使用普通 SELECT，不添加 FOR UPDATE。[MySQL 一致性读说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)

这与 10.1 写库事务的目的有区别：10.1 需要多次修改一起提交或回滚，10.2 主要需要多次读取使用一致的数据视图。

## 六、分页边界沿用原项目行为

当前项目原本配置了 `pagehelper.reasonable=true`，本次继续沿用：

- 页码、每页条数小于 1，业务校验失败。
- 状态不传则查全部；填写时只能是 1、2、3、4。
- 没有匹配订单，返回 total=0、items=[]。
- 页码超过最后一页，PageHelper 调整到最后一页。

最后一点是已有项目配置的行为，本次没有修改全局配置或另加不在文档中的每页条数上限。
