# 2.1 门店分页查询：实现与学习说明

本说明对应已实现的 `GET /admin/store/page`。接口参数和响应依据用户提供的 V1.0 PDF 第 2.1 节，登录与门店隔离依据通用说明第 0.2～0.4 节。

## 1. 先把需求变成一句话

当前登录员工，按照名称和营业状态筛选自己有权查看的门店，每次只取一页，同时返回符合条件的总条数。

例如：

```http
GET /admin/store/page?pageNum=1&pageSize=10&name=望京&status=1
Authorization: 登录接口返回的原始token
```

这是 GET 请求，参数写在 URL 的 `?` 后面；参数之间用 `&` 分隔，不需要 JSON 请求体。

| 参数 | 必填 | 含义 |
| --- | --- | --- |
| pageNum | 是 | 从 1 开始的页码 |
| pageSize | 是 | 每页条数，必须大于 0 |
| name | 否 | 名称包含此文字；未传、空串或纯空白表示不筛选 |
| status | 否 | 1 营业中，0 已打烊；未传表示两种都查 |

成功结果为：

```json
{
  "code": 0,
  "message": "操作成功",
  "data": {
    "total": 25,
    "items": []
  }
}
```

这里仅展示结构。`total` 是符合名称、状态和权限条件的全部门店条数，`items` 是本次查询所在页的数据。即使每页只返回 10 条，总数也可能是 25。没有匹配结果时，返回 `total=0` 和空数组。

## 2. 哪些文件负责什么

| 文件 | 作用 |
| --- | --- |
| controller/StoreController.java | 定义 URL，接收请求参数，返回统一响应 |
| service/StoreService.java | 定义门店分页业务方法 |
| service/impl/StoreServiceimpl.java | 校验参数、判断权限、启用分页、组装结果 |
| mapper/StoreMapper.java | 用 SQL 注解查询 t_store，参数为空时不限制对应条件 |
| pojo/Store.java | 一条门店记录的 Java 表示，已有 |
| pojo/PageBean.java | 保存 total、items，已有 |
| pojo/Result.java | 保存 code、message、data，已有 |

不要把所有逻辑放进 AdminController。AdminController 负责登录相关接口，门店管理使用 StoreController，后续新增、修改和删除门店可以继续放进 StoreController。

## 3. 从数据库层开始理解

Mapper 的核心查询如下：

```java
@Select("select * from t_store " +
        "where (#{name} is null or #{name} = '' or name like concat('%', #{name}, '%')) " +
        "and (#{status} is null or status = #{status}) " +
        "and (#{storeId} is null or id = #{storeId}) " +
        "order by id asc")
List<Store> list(@Param("name") String name,
                @Param("status") Integer status,
                @Param("storeId") Long storeId);
```

逐项解释：

- `@Mapper`：让 MyBatis 创建这个接口的代理对象，因此不用手写 StoreMapperImpl。
- `@Select`：告诉 MyBatis 调用 list 方法时执行哪条查询。
- `List<Store>`：查询结果是多条门店记录，每一行映射成一个 Store 对象。
- `@Param("name")`：把 Java 方法参数命名为 name，SQL 可以通过 `#{name}` 使用它。
- 写法与 EmployeeMapper 一致：SQL 直接放在 `@Select("...")` 中，较长时用 `+` 连接字符串。
- `#{name} is null or #{name} = '' or ...`：名称为空时该组条件成立，所有名称都允许；有名称时执行模糊匹配。
- `#{status} is null or status = #{status}`：状态未传时不限制；传了则必须匹配。
- `#{storeId} is null or id = #{storeId}`：超级管理员不限制门店编号，门店管理员只匹配本店。
- 每组 OR 条件用括号包起来，三组之间用 AND，确保筛选条件和门店归属同时成立。
- `like concat('%', #{name}, '%')`：例如 name=望京，形成 `%望京%`，查询名称包含“望京”的门店。
- `status=0`：0 不是 null，会正确筛选已打烊门店。
- `id = #{storeId}`：t_store 自己的门店编号是 id，员工表中的 store_id 才是所属门店编号。
- `order by id asc`：按照主键稳定排序，让分页有确定的顺序。

`#{...}` 使用绑定参数，不把输入直接拼成 SQL 代码。普通查询参数不要改成 `${...}`。

下面是按条件化简后的等价示意。实际执行的 SQL 会保留上面的 OR 条件，并使用绑定参数。

如果超级管理员只传 name=望京，查询效果相当于：

```sql
select * from t_store
where name like concat('%', ?, '%')
order by id asc
```

如果门店 1 的管理员同时传 status=1，查询相当于：

```sql
select * from t_store
where status = ? and id = ?
order by id asc
```

两个绑定值分别是 1 和 1。实际分页 LIMIT 由 PageHelper 添加。

已有的 `map-underscore-to-camel-case: true` 会把数据库的 open_time、create_time 等映射到 Store 的 openTime、createTime。Store 上的 JsonFormat 决定响应中的时间字符串格式。

## 4. Service 为什么还需要接口和实现类

StoreService 中的方法：

```java
PageBean<Store> page(Integer pageNum, Integer pageSize, String name, Integer status);
```

这个接口声明了“门店业务提供一个分页方法”。实现类 `StoreServiceimpl implements StoreService` 才负责执行具体步骤。

`@Service` 放在实现类上，让 Spring 创建并管理实现对象。

实现类通过构造方法接收 StoreMapper：

```java
private final StoreMapper storeMapper;

public StoreServiceimpl(StoreMapper storeMapper) {
    this.storeMapper = storeMapper;
}
```

只有一个构造方法时，Spring 会自动注入需要的对象，不必再写 `@Autowired`。final 表示依赖在构造时确定，之后不再重新赋值。

### 4.1 检查业务参数

Service 拒绝以下情况：

- pageNum 为 null 或小于 1。
- pageSize 为 null 或小于 1。
- status 既不是 null，也不是 0 或 1。

不合法时抛出 BizException，由现有 GlobalExceptionHandler 转成 `code=1` 的错误响应。

### 4.2 从登录信息确定权限

```java
Map<String, Object> claims = ThreadLocalUtil.get();
```

这个 Map 由 LoginInterceptor 从 JWT 解析得到，并在进入 Controller 前保存。客户端不需要再次提交自己的 role 或 storeId。

权限处理：

| 身份 | 查询条件 |
| --- | --- |
| role=1 超级管理员 | storeId=null，允许查询全部门店，再按名称和状态筛选 |
| role=2 门店管理员 | 从 JWT 获取 storeId，强制加上门店主键条件 |
| 缺少角色或其他角色 | 拒绝查询 |
| 门店管理员没有有效 storeId | 拒绝查询，不能退化为查全部门店 |

JWT 中整数解析出来可能是 Integer 或 Long，所以实现通过 Number 的 intValue、longValue 转换。

本接口文档只声明 pageNum、pageSize、name、status 四个请求参数，没有声明 storeId。即使前端额外传入 storeId=2，服务端也不会用它替换当前员工的所属门店。

name 通过 hasText 和 trim 处理，纯空白不形成筛选条件。

### 4.3 PageHelper 如何分页

```java
try (Page<Store> page = PageHelper.startPage(pageNum, pageSize)) {
    storeMapper.list(queryName, status, storeId);
    return new PageBean<>(page.getTotal(), page.getResult());
}
```

这几行分三步执行：

1. startPage 设置当前线程下一次查询的分页规则，并返回 Page 对象。
2. 调用 Mapper 时，分页插件先统计符合全部条件的总条数，再添加分页 SQL 并执行列表查询；总数和当前页记录写入 Page。
3. 从 Page 取出 total 和记录集合，放进项目约定的 PageBean。

startPage 本身没有立即查询数据库；真正触发查询的是 storeMapper.list。这里的 Mapper 返回值没有另存为 List，是因为 PageHelper 同时将结果填入了刚创建的 Page。

try-with-resources 会在退出代码块时调用 Page.close，清理分页上下文。即使 SQL 出错，也会执行清理。

对于 pageNum=2、pageSize=10，概念上相当于：

```sql
select count(*) from t_store where ...;
select * from t_store where ... order by id asc limit 10, 10;
```

偏移量公式为 `(pageNum - 1) * pageSize`。MySQL 的第一个 10 表示跳过 10 条，第二个 10 表示最多取 10 条。

真实生成的 SQL 可能使用参数占位符，或将 COUNT 包装为子查询，效果与上面的示意一致。

权限和筛选必须放在数据库条件中、分页之前执行。不能先分页查询所有门店，然后在 Java 中删掉其他门店，否则 total 和每页记录数会不正确。

不要在 startPage 和目标查询之间插入另一条 Mapper 查询，因为它可能先使用分页规则。参数检查和身份判断因此都放在 startPage 之前。

项目已有 `pagehelper.reasonable: true`：正数页码超过最后一页时会查询最后一页。本次保留该行为；小于 1 的页码由 Service 直接拒绝。

## 5. Controller 如何接收请求并返回结果

```java
@RestController
@RequestMapping("/admin/store")
public class StoreController {
    // 构造方法注入 storeService，完整代码见源码。

    @GetMapping("/page")
    public Result<PageBean<Store>> page(
            @RequestParam("pageNum") Integer pageNum,
            @RequestParam("pageSize") Integer pageSize,
            @RequestParam(value = "name", required = false) String name,
            @RequestParam(value = "status", required = false) Integer status) {
        PageBean<Store> pageBean = storeService.page(pageNum, pageSize, name, status);
        return Result.success(pageBean);
    }
}
```

以上为讲解用节选，完整类包含 storeService 字段和构造方法。

逐项解释：

- `@RestController`：处理请求，返回对象会被序列化成 JSON。
- 类的 `/admin/store` 加方法的 `/page`，构成 `/admin/store/page`。
- `@GetMapping`：只处理对应 GET 请求。
- `@RequestParam`：从查询字符串接收参数，默认 required=true，所以两个分页参数必须传。
- `required=false`：名称和状态可以不传，不传时为 null。
- `Integer`：Spring 将字符串 `"1"` 转换为整数；传 `abc` 会触发现有的参数类型错误处理。
- 调用 service：Controller 只接收参数，把业务交给 Service。
- `Result.success(pageBean)`：在分页数据外面加上 code、message、data。

返回类型可以从内向外理解：

```text
Store                 一条门店记录
List<Store>           当前页门店记录
PageBean<Store>        total + items
Result<PageBean<Store>> code + message + data
```

## 6. 用一次具体请求串起来

门店管理员登录后查询：

```http
GET /admin/store/page?pageNum=1&pageSize=10&name=望京
Authorization: 原始token
```

执行顺序：

```text
LoginInterceptor 校验 Redis 和 JWT
    ↓
把员工 role=2、storeId=1 等信息存入 ThreadLocal
    ↓
StoreController 将查询字符串转换为 Java 参数
    ↓
StoreServiceimpl 检查参数并确定只能查询门店 1
    ↓
PageHelper 设置第 1 页、每页 10 条
    ↓
StoreMapper 查询 name 包含“望京”且 id=1 的门店
    ↓
PageHelper 填充总数和当前页记录
    ↓
Service 创建 PageBean，Controller 用 Result 包装
    ↓
Spring 将对象转为 JSON
    ↓
拦截器清理登录 ThreadLocal
```

## 7. 在 Apifox 或 Postman 中怎么调用

1. 启动 MySQL、Redis，再在 IDEA 中运行 OrderingServerApplication。
2. 如果尚未初始化数据库，先确认环境并按项目原有方式初始化；不要在有业务数据的数据库上随意重跑建表脚本。
3. 调用 `POST http://localhost:8080/admin/login`，JSON 请求体传入合法员工用户名和密码。
4. 从成功响应的 data 复制 token。
5. 新建 GET 请求 `http://localhost:8080/admin/store/page`。
6. 在 Params 中填写 pageNum=1、pageSize=10，可选填 name、status。
7. 在 Headers 中填写 Authorization，值是原始 token，不加 Bearer 前缀。

如果数据库使用项目提供的初始化测试账号，可分别用 admin 和 store1 验证全部门店与本店查询。

常见结果：

| 请求情况 | 结果 |
| --- | --- |
| 未传 token 或 token 失效 | HTTP 401，响应体为空 |
| 未传 pageSize | code=1，提示缺少必传参数 |
| pageNum=abc | code=1，提示参数类型错误 |
| pageNum=0 或 pageSize=0 | code=1，提示必须大于等于 1 |
| status=2 | code=1，提示门店状态只能为 0 或 1 |
| 合法条件但没有门店匹配 | code=0，total=0，items=[] |


本接口测试不写入业务 MySQL 数据库，也不依赖实际 Redis 服务。H2 依赖的 scope 是 test，不会作为生产运行依赖。

## 9. 下次自己写接口时的顺序

1. 从文档列出请求方法、路径、必填参数、可选参数和返回结构。
2. 确定要查询的表和对应实体，先想清楚基本 SQL。
3. 编写 Mapper 方法，把可选条件和资源归属落实到 SQL 中。
4. 声明 Service 方法，在实现类中处理业务参数、权限和结果组装。
5. 编写 Controller，接收参数并调用 Service。
6. 对照文档验证正常请求、空结果、非法参数和越权请求。
