# 5.1 订单分页查询实现讲解

## 1. 接口和请求示例

```http
GET /admin/order/page?pageNum=1&pageSize=10&status=1
Authorization: 登录获得的原始token
```

在 Postman 或 Apifox 的 Params 中可以继续填写：

| 参数 | 示例 | 含义 |
| --- | --- | --- |
| pageNum | 1 | 页码，必传且至少为 1 |
| pageSize | 10 | 每页条数，必传且至少为 1 |
| status | 1 | 可选：1待接单、2已接单、3已完成、4已取消 |
| beginTime | 2026-10-11 00:00:00 | 可选：下单时间的下界 |
| endTime | 2026-10-11 23:59:59 | 可选：下单时间的上界 |

这是查询字符串，不是 JSON 请求体；测试工具会对时间字符串中的空格做 URL 编码。前端不传门店 ID，Service 从当前登录信息获取门店范围。

## 2. Controller：设置路由并解析时间

类上需要使用：

```java
@RestController
@RequestMapping("/admin/order")
```

你原来的 `@RestController("/admin/order")` 指定的是 Bean 名称，不能设置类级别请求路径。加上方法的 `@GetMapping("/page")` 后，实际路径才是 `/admin/order/page`。

时间参数这样接收：

```java
@RequestParam(value = "beginTime", required = false)
@DateTimeFormat(pattern = "yyyy-MM-dd HH:mm:ss") LocalDateTime beginTime
```

`endTime` 使用相同注解。`@DateTimeFormat` 处理 URL 参数到 LocalDateTime 的转换，格式错误或不存在的日期会返回参数类型错误。

它和 Order 实体上的 `@JsonFormat` 作用不同：`@JsonFormat` 由 JSON 序列化、反序列化使用，不能代替 URL 时间参数的格式声明。

## 3. Service：先校验，再开启一次分页

`OrderServiceimpl.page()` 的顺序是：

1. 检查 pageNum、pageSize 必填且大于等于 1。
2. status 不为空时，要求范围为 1 到 4。这里是订单状态，不是菜品的 0、1 上下架状态。
3. 两个时间都传入时，开始时间不能晚于结束时间，允许两者相同。
4. 调用 `AdminContextUtil.getCurrentAdminStoreId()`，检查登录、管理员身份、门店绑定，并获取本店 ID。
5. 调用 PageHelper 开启分页，下一条 MyBatis 查询就是要分页的订单查询。
6. 把总条数和当前页列表放进 PageBean，交给 Controller 包装 Result。

核心分页结构：

```java
try (Page<Order> page = PageHelper.startPage(pageNum, pageSize)) {
    orderMapper.list(storeId, status, beginTime, endTime);
    return new PageBean<>(page.getTotal(), page.getResult());
}
```

门店、状态、时间都在 SQL 中筛选，因此 total 是筛选后的总记录数，而不是取出一页数据再在 Java 中筛选。

## 4. 开始、结束时间不是创建、完成时间

这里的 beginTime、endTime 都是查询条件，分别表示订单下单时间的下界、上界，它们都作用于数据库的 `create_time`。

例如某订单 10 月 11 日下单，10 月 12 日才完成，查询 10 月 11 日下单的订单时仍应查到它。未完成订单的 finish_time 可以为 null，也应该能按下单日期查询。

因此正确条件是：

```sql
create_time >= #{beginTime}
create_time <= #{endTime}
```

两个边界都包含在结果中。只传开始时间就限制下界，只传结束时间就限制上界，都不传则不限制下单时间。

## 5. Mapper：参数名对齐，返回订单列表

```java
@Select("select * from t_orders " +
        "where store_id = #{storeId} " +
        "and (#{status} is null or status = #{status}) " +
        "and (#{beginTime} is null or create_time >= #{beginTime}) " +
        "and (#{endTime} is null or create_time <= #{endTime}) " +
        "order by id asc")
List<Order> list(@Param("storeId") Long storeId,
                 @Param("status") Integer status,
                 @Param("beginTime") LocalDateTime beginTime,
                 @Param("endTime") LocalDateTime endTime);
```

- 继续采用注解加字符串拼接的风格，排序沿用你原来的 ID 升序。
- SQL 中的占位符必须对应 `@Param` 指定的名称。既然使用 `@Param("beginTime")`，SQL 就要写 `#{beginTime}`。
- 返回类型改为 List<Order>，让 MyBatis 将查询结果映射为订单对象，供 PageHelper 获取当前页数据。
- store_id 是必选条件，不能因为前端传 storeId 或超管未绑定门店就放开本店查询范围。

## 6. 返回数据

Controller 返回 `Result.success(pageBean)`，data 中包含 total、items。Order 已有订单号、金额、状态、支付、取餐与时间字段，以及相应的 JSON 时间格式注解，本次复用这些字段。

接口不会修改订单，也不需要清理菜品列表缓存。

## 7. 本次与你前面写法的对比

这次你已经把登录人的 storeId 从 Service 传给 Mapper，并在 WHERE 中强制过滤门店；分页只开启一次，使用 try-with-resources 清理分页上下文。这些都是从前面接口中正确复用的部分。

需要继续核对的是新业务的含义：订单有 1～4 四种状态，时间条件表示区间，结束时间不是完成时间。Mapper 的返回类型、SQL 占位符，以及类级路由注解仍有遗漏，本次一起修正。

新增测试在独立 H2 内存数据库执行真实 SQL，并模拟 Redis，覆盖完整返回字段、四种订单状态、时间边界、单边和组合筛选、非法日期、时间区间倒置、门店隔离与分页上下文清理。真实 MySQL、Redis 联调尚未覆盖。
