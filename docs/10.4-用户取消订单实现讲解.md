# 10.4 用户取消订单：检查结果与实现讲解

接口是 `PUT /app/order/cancel/{id}`。顾客只能取消属于自己、当前仍为 1 待接单的订单，取消原因固定为“用户主动取消”。

## 一、和你上一次 10.3 相比

这次你已经主动写对了：

- Controller 使用 PUT 和路径参数，成功后返回 Result.success()。
- Service 从 UserContextUtil 获取当前 userId。
- 先检查 `id == null`，再比较 `id < 1`。
- 查询时传入 id 和 userId，判断订单是否存在且属于本人。
- 更新 SQL 已经想到用 `status=1` 限制状态。
- 取消原因的文本符合文档。

这些说明你正在把 10.3 的用户隔离与参数检查迁移到新功能。

本次需要补强的是写操作的结果判断、状态提示，以及查询到更新之间的并发保护。

## 二、原代码有哪些问题

原来的代码中：

```java
String cancelReason="用户主动取消"
```

末尾缺少分号。基线编译在该位置报“需要 ';'”。这次把原因固定写进 SQL，同时消除了这处语法错误。

原来的 Mapper 返回 void：

```java
@Update("update t_orders set status=4,cancel_reason=#{cancelReason} where id=#{id} and status=1")
void cancelByUser(Long id, String cancelReason);
```

你已经写了 status=1，因此其他状态不会被这条 SQL 改掉。但如果订单已接单，影响行数为 0，原方法仍正常返回，Controller 仍然返回成功。这就是“数据库没有修改，接口却报告成功”的问题。

另外还需要：

- 对已接单返回文档指定的失败提示。
- 在实际 UPDATE 中再次限定 user_id。
- 同时更新 update_time。
- 让 Mapper 返回影响行数，并检查恰好更新一行。
- 在事务中锁定目标订单，使状态检查和后续修改协调起来。
- 为多个 Mapper 参数显式声明 @Param，清楚对应 SQL 中的名字。

## 四、Service 按什么顺序执行

位置：[AppOrderServiceimpl 第 164 行](/D:/idea/Project/ordering-server/src/main/java/com/wys/orderingserver/service/impl/AppOrderServiceimpl.java:164)。

```java
@Transactional
public void cancel(Long id) {
    Long userId = UserContextUtil.getCurrentUserId();
    if (id == null || id < 1) {
        throw new BizException("请输入合法的订单ID");
    }
    Order order = orderMapper.findByIdAndUserIdForUpdate(id, userId);
    if (order == null) {
        throw new BizException("订单不存在或无权访问");
    }
    if (Integer.valueOf(2).equals(order.getStatus())) {
        throw new BizException("商家已接单，无法取消，请联系门店");
    }
    if (!Integer.valueOf(1).equals(order.getStatus())) {
        throw new BizException("当前订单状态不允许取消");
    }
    LocalDateTime now = LocalDateTime.now(ZoneId.of("Asia/Shanghai")).withNano(0);
    if (orderMapper.cancelByUser(id, userId, now) != 1) {
        throw new BizException("取消订单失败，请重试");
    }
}
```

第 170 行查询并锁定本人订单，返回 Order 实体。取消操作只需要读取并修改订单主表，不需要组装详情 VO。

第 174 行单独判断已接单，保证提示与文档一致。第 177 行拒绝已完成、已取消或其他非待接单状态。

第 182 行先调用更新方法，再检查返回的影响行数。写在 if 条件中的方法也会真正执行，不是只检查某个提前计算好的结果。

## 五、为什么这里查询时加 FOR UPDATE

位置：[OrderMapper 第 107 行](/D:/idea/Project/ordering-server/src/main/java/com/wys/orderingserver/mapper/OrderMapper.java:107)。

```sql
select * from t_orders
where id = #{id} and user_id = #{userId}
for update
```

它按当前用户限定目标订单，并在事务内锁定该订单行，读取最新状态。锁一直保持到本次事务提交或回滚。[MySQL 锁定读说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

这里随后只更新同一个订单行，不再去取得门店锁。管理端接单虽然先锁门店再锁订单，但用户取消持有订单锁后不会反过来等待门店锁。

如果商家正在接单并持有订单锁，用户取消会等待；商家提交后，用户读取到新的已接单状态，返回文档要求的失败信息。

## 六、更新 SQL 如何保护数据

位置：[OrderMapper 第 111 行](/D:/idea/Project/ordering-server/src/main/java/com/wys/orderingserver/mapper/OrderMapper.java:111)。

```java
@Update("update t_orders set status = 4, cancel_reason = '用户主动取消', update_time = #{updateTime} " +
        "where id = #{id} and user_id = #{userId} and status = 1")
int cancelByUser(@Param("id") Long id,
                 @Param("userId") Long userId,
                 @Param("updateTime") LocalDateTime updateTime);
```

WHERE 中三个条件分别表示：

| 条件 | 意义 |
| --- | --- |
| id | 只操作指定订单 |
| user_id | 必须属于当前顾客 |
| status=1 | 必须仍然待接单 |

传入当前用户 ID 后，即使直接调用 Mapper、不经过前面的 Service 状态检查，这条 UPDATE 也不会修改不属于该用户的订单或覆盖其他状态。

修改字段仅有 status、cancel_reason、update_time。原支付状态、支付时间、完成时间、金额、备注、订单明细和购物车保留原值。

## 七、不同状态返回什么

| 订单情况 | 行为 |
| --- | --- |
| 本人待接单 | 改为 4，返回成功 |
| 本人已接单 | 返回“商家已接单，无法取消，请联系门店” |
| 本人已完成 | 返回“当前订单状态不允许取消” |
| 本人已取消 | 返回“当前订单状态不允许取消”，不覆盖原取消原因 |
| 他人的订单或不存在 | 统一返回“订单不存在或无权访问” |

文档只允许 1 → 4，因此重复取消不会再次返回成功，也不会改写首次取消时间。门店是否已打烊不影响取消本人待接单订单。

## 八、与商家接单、后台超时取消同时发生怎么办

这三种操作都只能从待接单状态出发，通过数据库行锁和 SQL 原状态条件协调。

| 先提交的操作 | 后续结果 |
| --- | --- |
| 用户取消 | 商家不能再接单；超时扫描不会覆盖“用户主动取消”原因 |
| 商家接单 | 用户取消读取到状态 2，返回文档中的已接单提示 |
| 超时取消 | 用户取消读取到状态 4，拒绝操作，保留超时原因 |

本次不需要给取消动作另外加 Redis 锁。Redis 继续负责已有的登录状态检查，取消业务自身由数据库事务协调。

## 九、为什么要有事务和影响行数检查

事务把“锁定订单、检查状态、执行更新”放在同一段业务中，锁不会在查询结束后立刻释放。

更新影响行数必须为 1。若不是 1，就抛 BizException，让 Controller 不再误报成功。

测试还覆盖了这种情况：SQL 已经更新订单，但随后返回异常影响行数，或抛数据库异常。事务会撤销刚才的更新，使订单保持原样。
