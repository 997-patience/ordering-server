# 9.1 用户端购物车列表实现讲解

本接口是 `GET /app/cart/list`，查询“当前登录顾客自己的购物车”。`storeId` 可选：传入时查看自己在这家店的购物车，不传时查看自己在各门店的全部购物车项。

## 一、与你上次的实现相比

你在 8.4 初写时把路径菜品 ID 当成了查询参数中的门店 ID。这次已经正确使用 `@GetMapping("/list")`、可选 `@RequestParam` 和列表返回类型，也写出了 Controller → Service → Mapper 的完整调用链。

这次需要完善的是个人数据范围，以及关联查询返回字段：

| 原实现 | 修改后 | 原因 |
| --- | --- | --- |
| SQL 只按门店 ID 查询 | 始终按当前用户 ID 查询，门店可选 | 同一家店的不同顾客不能看到彼此的购物车 |
| `store_id = coalesce(#{storeId}, null)` | `#{storeId} is null or c.store_id = #{storeId}` | 不传门店时应取消门店筛选，而不是与 NULL 比较 |
| `select * from t_cart` 返回 `Cart` | 购物车表关联菜品表，返回 `CartItemVO` | 文档还要求名称、图片、单价、小计 |
| 根据门店是否为空写两条调用分支 | 一次调用统一查询 | SQL 已经支持可选门店 |

从 8.x 到 9.x，查询对象发生了变化：门店和菜品供顾客浏览，购物车则属于某一个顾客。判断“数据属于谁”要放在确定查询条件之前。

## 二、两个 ID 分别从哪里来

```text
userId：我是谁 → 登录 token → 拦截器解析验证 → ThreadLocal
storeId：我想看哪家店 → URL 查询参数
```

例如：

```http
GET /app/cart/list?storeId=1
Authorization: 用户登录返回的完整 token
```

假设 token 表示用户 8，那么查询条件应当是：用户 8，并且门店 1。

即使前端添加 `userId=9`，也不会改变查询的用户，因为 Controller 不接收它，Service 从登录信息取得用户 ID。

## 三、Controller：接收可选门店，返回数组

```java
@GetMapping("/list")
public Result<List<CartItemVO>> find(
        @RequestParam(value = "storeId", required = false) Long storeId) {
    List<CartItemVO> carts = cartService.find(storeId);
    return Result.success(carts);
}
```

类上的路径是 `/app/cart`，与方法路径 `/list` 组合成完整地址。`required = false` 表示不要求必须提供门店；没有传入时 `storeId` 为 null。

## 四、Service：先取得当前用户，再查询

```java
public List<CartItemVO> find(Long storeId) {
    Long userId = UserContextUtil.getCurrentUserId();
    if (storeId != null && storeId < 1) {
        throw new BizException("请选择有效的门店ID");
    }
    return cartMapper.listByUserIdAndStoreId(userId, storeId);
}
```

新增 `UserContextUtil`，与已有管理员上下文工具分工：它从当前请求的 ThreadLocal 读取顾客身份，检查 `type=user`，并取得正整数用户 ID。JWT 还原整数时可能得到 Integer 或 Long，最后统一转换为 Long。管理员身份、缺失身份和无效用户 ID 不能通过这个入口查询购物车。

JWT 签名、Redis 令牌及用户是否仍然存在的校验，继续由已有 `LoginInterceptor` 完成。请求结束仍由拦截器清理 ThreadLocal。

门店 ID 可以不传，但传入 0 或负数会被拒绝。缺少身份、参数错误都在进入购物车 SQL 之前处理。

## 五、Mapper：始终保留用户条件

```java
@Select("select c.id, c.dish_id, d.name, d.image, d.price, c.quantity, " +
        "d.price * c.quantity as amount " +
        "from t_cart c inner join t_dish d on d.id = c.dish_id and d.store_id = c.store_id " +
        "where c.user_id = #{userId} " +
        "and (#{storeId} is null or c.store_id = #{storeId}) " +
        "order by c.id asc")
List<CartItemVO> listByUserIdAndStoreId(
        @Param("userId") Long userId,
        @Param("storeId") Long storeId);
```

`c` 是购物车表的简称，`d` 是菜品表的简称。

### 1. 关联菜品信息

```sql
inner join t_dish d
on d.id = c.dish_id and d.store_id = c.store_id
```

购物车表保存“谁选了哪道菜、数量多少”，菜品表保存“这道菜叫什么、图片是什么、当前单价多少”。两张表关联后才能组合出接口要求的完整结果。

额外核对双方门店一致，避免异常购物车条目关联到不同门店的菜品。INNER JOIN 不会返回没有匹配菜品的条目；正常删除菜品时，项目已有代码会同时清理对应购物车引用。

### 2. 当前用户条件不能省略

```sql
where c.user_id = #{userId}
```

例如购物车中有：

| 购物车项 | 用户 | 门店 | 菜品 |
| --- | --- | --- | --- |
| 1001 | 小明 | 门店 1 | 宫保鸡丁 |
| 1002 | 小红 | 门店 1 | 宫保鸡丁 |
| 1003 | 小明 | 门店 2 | 其他菜品 |

小明查询门店 1 时只能得到 1001。不传门店时得到 1001、1003。两种情况都不能得到小红的 1002。

### 3. 可选门店怎样实现

```sql
and (#{storeId} is null or c.store_id = #{storeId})
```

- 不传门店：左侧为 true，这个条件不限制门店。
- 传门店 1：左侧为 false，必须满足右侧“门店等于 1”。

无论是否传门店，上面的 `user_id` 条件始终保留。

原来的 `coalesce(#{storeId}, null)` 在参数为空时仍然得到 null，最终相当于 `store_id = NULL`。SQL 中这不会得到 true，因此无法表达“全部门店”。

### 4. 小计怎样计算

```sql
d.price * c.quantity as amount
```

单价 38.00、数量 2，小计就是 76.00。这里使用数据库 DECIMAL 金额乘整数，结果映射到 Java BigDecimal；没有转成 double。测试同时覆盖 0.10 × 3 = 0.30。

排序按购物车项 ID 升序，保持结果稳定。

## 六、为什么新增 CartItemVO

原来的 `Cart` 对应购物车表，没有菜品名称、图片、单价和小计。

`CartItemVO` 对应本接口的一条返回数据，只包含：

```text
id、dishId、name、image、price、quantity、amount
```

MyBatis 把关联查询结果直接映射到该对象，`dish_id` 按项目已有驼峰映射转换成 `dishId`。用户 ID、门店 ID 和创建、更新时间不额外返回。

本次没有为个人购物车套用菜品列表缓存；每次查询读取当前菜品名称、图片和价格。文档没有要求过滤下架菜品，因此已有购物车项仍可出现在列表中。空购物车或指定门店没有匹配项时返回成功和 `data: []`。

## 七、完整执行过程

```text
GET /app/cart/list?storeId=1
→ 拦截器验证顾客 token，将身份放入 ThreadLocal
→ Controller 接收门店 1
→ Service 通过 UserContextUtil 取得当前用户 ID
→ Mapper 按当前用户、可选门店查询，并关联菜品
→ SQL 计算 price × quantity
→ 映射为 List<CartItemVO>
→ Controller 返回 Result.success(carts)
→ 拦截器清理 ThreadLocal
```

这次只完成 9.1，没有提前实现 9.2 加购或其他购物车操作。

自动测试使用独立 H2 执行真实 SQL，Redis 使用带状态的模拟对象。重点覆盖同店不同用户、同菜不同数量、不传门店、伪造 userId、异常身份、精确金额、实时价格、门店不匹配和参数边界。此验证不等同于真实 MySQL、Redis 环境联调。
