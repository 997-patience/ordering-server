# 7.2 用户登录实现讲解

本次完成 `POST /app/login`。前端提交手机号、密码，服务端验证成功后，在 `data` 中返回 JWT 字符串。前端在后续请求的 `Authorization` 请求头中携带这个字符串。

## 一、先把登录当成“领通行证”

可以这样理解整个过程：

1. Controller 是窗口，接收手机号、密码。
2. Service 是审核人员，检查账号和密码。
3. Mapper 查询数据库中的用户资料。
4. 验证通过后，JWT 是发给前端的通行证，Redis 保存这张通行证的有效记录。
5. 下一次请求，拦截器检查通行证，把当前身份临时放入 ThreadLocal。
6. 本次请求结束，清空 ThreadLocal。下一次请求再从 token 恢复身份。

**ThreadLocal 只服务于当前请求，不会帮用户跨请求保存登录状态。跨请求时靠的是前端携带 token。**

## 二、与你这次已经写出的代码对比

你已经写出了按手机号查用户、验证密码、从数据库用户中取身份信息、组装 claims，以及生成 JWT。这些构成了登录业务的主要步骤。

这次主要补上以下部分：

| 原来的状态 | 完善后的行为 | 为什么需要 |
| --- | --- | --- |
| Service 返回 `void`，token 只是局部变量 | Service 返回 `String`，Controller 把 token 放入 `Result.data` | 前端必须拿到 token 才能发起后续请求 |
| 生成 JWT 后没有写入 Redis | JWT 和 Redis 均使用 12 小时有效期 | 拦截器会检查 Redis，没保存就会被拒绝 |
| 未注册、手机号错误、密码错误分别提示 | 认证失败统一提示“手机号或密码错误” | 与 7.2 文档保持一致 |
| 空密码可能在字符串比较时出问题 | 先检查空值，再使用已有的 `Md5Util.checkPassword` | 避免空指针，认证失败返回明确结果 |
| 用户端开始有 `type=user`，管理员令牌没有对应标记 | 新管理员令牌补充 `type=admin`，拦截器按身份限制访问路径 | 顾客和员工可能具有相同的数字 ID，必须区分身份 |
| 主要关注本次登录的 ThreadLocal | 同时验证后续请求的身份恢复与清理 | 登录成功以后，其他接口才能读取当前用户 |

相比你上次只完成 ThreadLocal 填充时，现在你的代码已经主动写到了 JWT 生成这一步。接下来最需要练习的是顺着“谁调用谁、谁返回给谁”检查完整流程：一个局部变量生成出来以后，还要通过返回值传到调用方。

## 三、Controller：接收请求，把 token 返回前端

位置：`src/main/java/com/wys/orderingserver/controller/app/AppLoginController.java`。

```java
@PostMapping("/login")
public Result<String> login(@RequestBody User user) {
    try {
        String token = userService.login(user);
        return Result.success(token);
    } finally {
        ThreadLocalUtil.remove();
    }
}
```

类上的 `@RequestMapping("/app")` 和方法上的 `/login` 合起来就是 `/app/login`。`@RequestBody` 把 JSON 转成 `User`。

`Result<String>` 表示 `data` 的类型是字符串。`Result.success(token)` 会把 token 放入 `data`，并设置成功的 `code` 和 `message`。

登录只需要手机号、密码，不要求昵称，所以这里没有使用注册时的 `@Validated(User.Add.class)`。登录必要参数由 Service 检查。

登录在拦截器白名单中，不会执行拦截器的清理逻辑。因此 Controller 用 `finally` 清理本次登录请求的 ThreadLocal，成功、失败都会执行。

## 四、Service：验证身份、签发并保存 token

位置：`src/main/java/com/wys/orderingserver/service/impl/UserServiceimpl.java`。

### 1. 先处理没有填写的参数

```java
if (user == null || !StringUtils.hasText(user.getPhone())
        || !StringUtils.hasText(user.getPassword())) {
    throw new BizException("手机号或密码错误");
}
```

`hasText` 要求字符串存在，并且至少有一个非空白字符。这里不把密码 `trim`，因为验证密码应该比较用户实际输入的内容。

### 2. 查询用户，验证密码

```java
User existingUser = userMapper.findByPhone(user.getPhone());
if (existingUser == null
        || !Md5Util.checkPassword(user.getPassword(), existingUser.getPassword())) {
    throw new BizException("手机号或密码错误");
}
```

`existingUser` 来自数据库。`user` 来自请求，它们不是同一个对象。

如果用户不存在，`||` 会短路，后面的密码比较不会执行。存在时，`checkPassword` 将输入密码计算成 MD5，再与数据库保存的值比较，沿用本项目注册时的密码规则。

这里已经按手机号查询，不需要再写一次“输入的手机号是否等于查到的手机号”。

Service 抛出的 `BizException` 会由现有 `GlobalExceptionHandler` 转换成：

```json
{"code":1,"message":"手机号或密码错误","data":null}
```

### 3. 组装可信的身份信息

```java
Map<String, Object> claims = new HashMap<>();
claims.put("id", existingUser.getId());
claims.put("phone", existingUser.getPhone());
claims.put("nickname", existingUser.getNickname());
claims.put("type", "user");
String token = JwtUtil.genToken(claims);
```

ID、手机号、昵称都取自数据库用户。即使请求体提交别人的 ID 或昵称，也不会覆盖实际登录身份。密码不放入 JWT，管理员角色和门店权限也不从请求体读取。

`type=user` 代表顾客，`type=admin` 代表管理员。两个表都可能有 `id=1`，加上类型后才能明确是哪一类账号。

### 4. 先保存 Redis，再返回 token

```java
stringRedisTemplate.opsForValue()
        .set(token, token, JwtUtil.EXPIRE_SECONDS, TimeUnit.SECONDS);
ThreadLocalUtil.set(claims);
return token;
```

项目约定 Redis 的 key 和 value 都是 token。`EXPIRE_SECONDS` 是 43200 秒，也就是 12 小时，与 JWT 的有效期相同。

Redis 保存失败时，Service 返回“登录服务暂不可用，请稍后重试”，不会向前端返回一个无法通过拦截器检查的 token。ThreadLocal 在 Redis 保存成功之后才填充。

接口 `UserService` 和实现类的返回类型都已经由 `void` 改为 `String`，Controller 才能接住这里的 `return token`。

## 五、Mapper → 数据库：复用你已写好的查询

位置：`src/main/java/com/wys/orderingserver/mapper/UserMapper.java`。

```java
@Select("select * from t_user where phone = #{phone}")
User findByPhone(@Param("phone") String phone);
```

传入的 `phone` 来自请求里的手机号。`#{phone}` 使用参数绑定，MyBatis 执行查询后把一行结果映射为 `User`；没有结果则返回 `null`。手机号有唯一索引，因此一次查询最多找到一个用户。

登录查询不需要新增 SQL，也不需要写入用户表。本次复用了你现有的 Mapper。

## 六、下一次请求：拦截器恢复身份

位置：`src/main/java/com/wys/orderingserver/interceptors/LoginInterceptor.java`。

前端请求受保护接口时，添加：

```text
Authorization: 登录响应 data 中的完整 token
```

沿用本项目原来的约定，直接传 token 字符串。

拦截器按顺序执行：

1. 清理可能残留的 ThreadLocal，读取请求头。
2. 检查 token 是否还在 Redis 中。
3. 验证 JWT 签名和有效期，解析 claims。
4. 根据 `type` 区分顾客和管理员，禁止互访受保护的另一端接口。
5. 顾客按手机号查数据库，并核对用户 ID；员工继续检查是否存在、是否启用。
6. 把通过检查的 claims 放入 ThreadLocal，业务代码才能读取当前身份。
7. 请求完成后，在 `afterCompletion` 清理 ThreadLocal，包括业务抛异常的情况。

为了兼容之前已签发的管理员令牌，只有 `role`、没有 `type` 的旧管理员令牌仍可访问管理端；用户端受保护接口要求明确的顾客身份。

## 七、如何验证

请求示例，手机号需要先通过 7.1 注册：

```http
POST /app/login
Content-Type: application/json

{"phone":"13800000001","password":"123456"}
```

成功响应：

```json
{"code":0,"message":"操作成功","data":"实际生成的 JWT 字符串"}
```

错误密码或未注册手机号应得到文档中的“手机号或密码错误”；缺失或错误 JSON 则由现有全局异常处理器提示请求体格式错误。

自动测试使用独立 H2 数据库执行真实 MyBatis 查询，模拟 Redis 保存、读取和删除令牌，覆盖注册后登录、正常登录、输入错误、身份伪造、令牌互访、令牌失效和上下文清理。测试中的身份观察接口只存在于测试上下文。

这些验证不等同于真实 MySQL、Redis 环境联调。手动联调前需要启动项目所配置的数据库和 Redis，并使用实际注册的账号。
