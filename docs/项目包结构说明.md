## 2. 从哪几个文件开始写用户注册

7.1、7.2 的调用链预留为：

```text
controller.app.AppLoginController
          ↓
service.UserService
          ↓
service.impl.UserServiceimpl
          ↓
mapper.UserMapper
```

AppLoginController 的类级路径保留 `/app`。后续分别在方法上添加 `/register`、`/login`，对应文档中的 `/app/register` 和 `/app/login`。

UserController 是原有空类的迁移预留，注册登录统一放在 AppLoginController，避免同一个 URL 写两份。

## 3. 用户端与管理端订单为什么分开

```text
管理端 OrderController    → OrderService    → OrderMapper
用户端 AppOrderController → AppOrderService → OrderMapper
```

两端共用订单表和 Mapper，但业务权限不同：商家处理本门店订单，顾客处理自己的订单。现有管理端 Service 使用 AdminContextUtil，不能用这套管理员角色校验来识别顾客。

Service 和 impl 继续放在现有包下，用户端同名业务使用 App 前缀。这样可以清楚地区分 AppOrderServiceimpl 和 OrderServiceimpl，也不会因两个同名 @Service 类产生默认 Bean 名称冲突。

## 4. 目录位置与 URL 的关系

包名负责代码归类，URL 由 @RequestMapping、@GetMapping 等注解决定。管理员登录类从 controller.app 移到 controller.admin 后，已有 `/admin/login`、`/admin/info`、`/admin/logout` 路径仍由原来的注解定义。

上传属于公共入口，因此放在 controller.common；按文档保留 `/admin/upload` 的类级路径，实际上传方法仍留到 11.1 再写。

所有新包都位于启动类所在的 com.wys.orderingserver 之下，沿用现有 Spring 扫描即可。

## 5. 当前完成范围

- 管理端六个 Controller 完成位置与 package 声明调整，原业务方法保留。
- 用户端和上传 Controller 仅包含类声明及适用的类级注解，没有新增 HTTP 处理方法。
- 用户端 Service 和实现仅建立接口、implements 对应关系和 @Service 注解，没有业务方法。
- 原先空白的 UserMapper、OrderDetailMapper 建立包声明和 @Mapper 接口，没有 SQL。
- 整理 AppLoginController 时移除了未写完的单独一行 private，使空壳能够编译。

因此，目录准备好不代表用户注册、购物车、下单或上传功能已经实现。后续按接口文档顺序逐个补方法即可。
